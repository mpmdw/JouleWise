## Conflict resolutions

1. **`docs/process_traces/2026-10-07-block5-seal/SEAL_RECORD.md`.** The lane added an unnumbered paragraph, the
   Q-RENDERER declared deviation (2026-10-20), inside "Release event". Main appended "Addendum 5: F7 meter
   cross-check" (2026-10-22). The resolution keeps the lane's paragraph where the lane put it, then main's Addendum 5.
   Both are in date order and nothing was renumbered. The lane's file is a byte-exact prefix of the result, and the
   result differs from main only by the inserted paragraph.
2. **`scripts/digest_pin_census.py`.** Main's EraSpec, `scope_text`, `era_spec`, `expected_count` and the
   inventory/registration pairing are kept. The lane's era records are ported into main's form:
   - `configs/analysis/b5/seal_pins.json` is added to `ERA_RECORDS` with the lane's `commit_pointer_template`
     (`/pins/\g<pin>/head`) and scope pointer. `EraSpec` gains `commit_pointer_template`.
   - The lane's `sealed_inventory.json` entry was already on main (`^/files/.+$`, `expected_count` 682). Main's
     entry is kept unchanged.
   - `_era_commit` expands the template from the literal's pointer, through the new `_commit_pointer`.
     `era_commit` also accepts a bare pointer string, the lane's calling form, alongside main's `Literal`.
   - The census caches one commit per claim through the new `era_claim(path, spec, pointer)`. The key is
     `(id(spec), expanded pointer)`, so each pin resolves at its own head. Caching by `id(spec)` alone would have
     bound every pin to the first pin's head.
   - `validate_era_records` skips the document-level commit for template specs. As in the lane, those heads are
     checked per literal by the census and by `--check`.
   - No `expected_count` is set for seal_pins: the lane had none, and the miniature-tree tests use a different
     literal count.
3. **`scripts/repin.py`.** Main's per-literal `era_spec` lookup is kept. Its cache key becomes
   `(path, *census.era_claim(path, spec, pointer))` for the same per-pin reason.
4. **`configs/pins/registry.json`.** Started from main's file, then rewritten by `python3.13 scripts/repin.py --write
   registry` on the merge tree. The 21 seal_pins rows equal the lane's rows exactly, each at its pin's head. The 682
   sealed-inventory rows equal both parents'. The other differences come from both parents' committed registries
   being stale:
   - Main's own registry, regenerated on main alone, changes 42 rows. One example: `joulewise/interfaces.py`
     changed in fa85af5c2 after main's last refresh.
   - The lane never registered `configs/analysis/b5/analysed_windows.json`. It now has 11 unresolved
     `harvest_record_sha256` rows, which are records of harvests that are not in the repository.

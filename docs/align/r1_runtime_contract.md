# ALIGN v4 R1 runtime contract (WP15 seam)

The R1 driver (`scripts/align_r1_rehearsal.py`) does no model, SMC or gate work itself. For each segment it runs the WP15 runtime argv once:

    <runtime...> --r1-kind KIND --output DIR [--duration-s N] [--soak-reference FILE]

It then reads one JSON object from stdout. A non-zero exit, a result that is not JSON, or a missing field refuses R1 (exit 3). The Automatic power mode is still restored.

The runtime argv is the list `inputs.WP15.runtime_entrypoint` in `configs/campaigns/align_v4/registration/inputs.json` (Fable cold pass LOW-3):

    ["scripts/align_r1_runtime.py", "--config", "configs/align/v4/r1_runtime.json"]

Element 0 is a repo-relative Python script; the chain passes `--runtime-entrypoint <inputs.json>` and the driver runs it with its own interpreter (`$PY -B`, the pinned venv), followed by the remaining elements verbatim. `ALIGN_R1_RUNTIME`, if set, overrides the list with one operator-pinned executable path (never shell text); this is the only place the override is defined.

The field table lives in `joulewise/align/apple/r1_runtime_contract.py` (`KIND_FIELDS`, `QUIET_FIELDS`, `NEEDS_SOAK_REFERENCE`). The driver checks every result against it at the seam. This document is the prose form of that table, and a test keeps the two in step.

## Arguments

- `--output DIR` is always the canonical segment directory, `<R1 output>/<segment name>`. When the driver rejects an attempt (ruling 8 load, or soak slope), it renames that directory to `<segment name>.rejectedN` (the next free N from 1) before the next attempt starts. A step-d or designed start state whose G0 timed out is moved to `<segment name>.g0_timeout1` before its one retry (LEAD-RULINGS-2 R6-2). The accepted attempt therefore always ran in, and owns, the canonical directory. The runtime must write only inside `DIR` and use paths relative to it.
- `--soak-reference FILE` is passed to every invocation after the accepted idle soak. The file is `<R1 output>/soak_reference.json`, schema `joulewise.align.r1_soak_reference.v1`, and holds:
  - `sensors_c`: per sensor key, the mean over the last 1,200 s of the accepted soak. This is the reference R.
  - `detrended`: the slope, SD and mean per key.
  - the source attempt.

  Every release, the post-D cooldown, the calibration precools (R6-2), X-G, the gated D runs, the designed planning-turn start states and the A-B-A legs measure against this R. The kinds marked "R" below refuse without it. No R1 model member keeps a self-captured reference: each installs R (or its designed start state) through a session hook before warmup, so the gate policy's `capture` role never fires (LEAD-RULINGS-2 R5-1).
- `--duration-s N` is given for fixed-length idle segments only.
- The kinds that run D under the R1 slots (`x-g`, the gated D runs) read the accepted step-d result, `<R1 output>/step_D_prefill_10k_decode_4096/runtime_result.json`, for T_dead, B_D, N_chunk and G_turn. They refuse without it, and they refuse unless its bytes are the ones the step-d runtime's own `runtime_custody.json` (status `complete`) digested (Sol wp15rev F3: a post-close edit of B_D, N_chunk or T_dead is refused). Reading a sibling is the runtime's only access outside `DIR`.
- A gated D run never runs unbudgeted (lead ruling R5-4): it refuses (exit 2, before any model work) unless the step-d `B_D` is a multiple of 1,024 in [1024, 40960] and `T_dead` is finite and positive. step-d floors a small budget to 0, so the driver checks the same rule right after step-d and refuses there, before the cooldown, X-G and the gated runs; it also refuses there when any slot is not finite (a no-rise t63 is null, below).

## Signals and custody (Fable cold pass MEDIUM-1)

- On its first TERM/INT/HUP the driver sends TERM to the running runtime, waits at most 20 s (inside run_night's 30 s), and only then sends KILL. Later signals are ignored so the wait and the Automatic restore complete.
- On TERM the runtime must stop work and, within 20 s: let an open controller bundle salvage and finalize (that stops powermetrics and closes the bundle's SMC sidecar), close its own SMC sessions, heater and journals, write its terminal record and exit 128 + signal. The WP15 runtime forces its own exit after 15 s.
- The terminal record is `DIR/runtime_custody.json` (`status`: `complete`, `refused`, `failed` or `aborted`, the signal, and the SHA-256 of every other file in `DIR`; a file of the same name below `DIR` is digested like any other, Sol wp15rev F2). It is written last on every exit path. On the 15 s watchdog path (executing review round 4 LOW-1) the runtime first sends TERM to every `powermetrics` process in its own process tree (the `sudo` child relays it to the root `powermetrics`), then writes the record with `status: aborted`, `watchdog: true` and the pids it signalled; digests that would run past a 1.5 s deadline (checked per 1 MiB block) are listed as `unhashed: watchdog deadline`. A pid is signalled only if a second process snapshot still shows it in the runtime's tree with the same parent and command. One writer owns the terminal record: if the watchdog publishes, the normal path never replaces it, and the watchdog never overwrites a normal record. An independent hard exit 4 s after the watchdog fires bounds even a stalled teardown, so the forced exit stays inside the driver's 20 s grace. A teardown that a first signal interrupts still closes every remaining session (the powermetrics stop included) and the load journal (Sol wp15rev triage). After an abort `DIR` is incomplete: it holds the salvaged bundle and journals, and the custody record says so. Nothing is printed on stdout unless the segment completed.
- The runtime refuses (exit 2) when `DIR` already exists, an input is PENDING (R0 sensor keys, the kit's R0 reasoning effort, WP18's X-G turn count, the D-4bit source) or `--soak-reference` is missing or unreadable; it exits 3 when the segment ran but cannot supply its fields.

## Fields every quiet segment returns (council ruling 8)

The quiet segments are:
- the idle soak;
- the 30B and D step tests;
- the three planning-turn states;
- the three A-B-A legs.

Each returns:

| field | type | meaning |
|---|---|---|
| `cpu_busy_cores` | list of finite numbers, 1 per second | Background CPU load in cores: summed %CPU / 100 of every process outside the measured runtime's own process tree. The driver redoes the segment when the load is > 0.5 core for 60 consecutive seconds. |
| `cpu_busy_t_s` | list of finite numbers, same length | The time of each `cpu_busy_cores` sample in seconds on the segment's own clock (nondecreasing). |
| `census` | non-empty list | Process census: the full process table at least at segment start and end. |

The journal must cover the segment (executing review MEDIUM-1). With W the wall seconds the driver measured around the invocation, R1 refuses unless there are at least 0.9·W − 5 samples and no two consecutive sample times are more than 5 s apart. Without that, one sample could stand for an 1,800 s soak and the 60 s-sustained rule would be vacuous.

`LoadJournal` in the contract module is the reference implementation of these fields. Each ruling 20 census retries one failed `diskutil info` per mount before it counts the mount as unmeasured (executing review round 4 LOW-3); the failure stays on the record (`diskutil_failures`). It uses `ps -A -o pid=,ppid=,pcpu=,comm=` and excludes the runtime's PID tree. A redo of a heavy segment starts only after a `g0-release-soak` release, never straight after the contaminated attempt.

## How the driver uses the fields

- **U5 (ruling 6 with lead ruling L2, c = 1.0).** Inputs:
  - σ_pair = max(|E_a − E_b|, 2.97 J), where E_a and E_b are the `energy_j` of the two spam/benign replay runs;
  - δ_slow is the planning-turn `delta_slow_c`.
  - a replay run that admitted no turn (its G0 did not release, so `energy_j` is 0) makes |E_a − E_b| meaningless; U5 is then INCONCLUSIVE with `sigma_pair_valid: false` and the reason (round-4 executing review HIGH-2).

  The verdict:
  - PASS if |β_T|₉₀·δ_slow ≤ σ_pair;
  - FAIL if |β_T|·δ_slow > σ_pair;
  - INCONCLUSIVE otherwise.
- **Order (LEAD-RULINGS-2).** calibration-pre, idle soak, 30B step (no separate cooldown after it: R6-6), the A-B-A legs, then **under the adopted series mode** (High Power if A-B-A adopts, else Automatic; protocol v4 :243-251, R5-5): the step-d precool, step-d, the post-D cooldown (ruling 1(c)), the designed start states **warmest first** (R + 4, R + 2, R + 0 °C, R5-2), each after a precool to the G0 band of R (the post-D cooldown for R + 4; R6-2), then the three gated D runs and X-G back to back (R6-1: the R + 0 °C planning turn is the D turn before the first gated run, and X-G follows D_bank, W1's D → X transition), the optional 4-bit, then Automatic is restored before calibration-post and the harvest. Each A-B-A leg must record its leg mode, and each model member after the decision the series mode, as an observed integer (ruling 7; an unobserved value refuses R1); `r1_slots.slots_ac_powermode` records it and the kit requires it to equal `ac_powermode`.
- **Thermometry bar (protocol v4 :243-251, R5-5).** Around both planning-turn steps (30B and D) the runtime journals every inventoried `T*`/`F*` key at 1 Hz (`DIR/inventory/inventory_journal.jsonl`) from before the member through a fixed 600 s recovery; the step member idles 300 s after its G0 release, so the last 300 s before prefill are quiet. The WP14(a) classifier (`smc_enumeration.rank`, stage `r1`) runs on idle = the 300 s before prefill dispatch, load = prefill dispatch to the last decode, recovery = 600 s. The D classification fills `r1_slots.thermometry` (`bar`: pass only with both picks; `r1.sensor_pick_changed` when a pick differs from R0's); the 30B one is recorded only. The kit refuses W1 unless the bar passed, unless W1's gate keys (`R1.thermal_policy.sensors`) are in the D classification's die and heatsink lists, and, when R1 changed (or did not report) R0's picks, unless the lead recorded `thermometry.lead_verification`. For changed picks the runtime also computes `thermometry.s7_for_r1_picks` from the inventory journal (reference = the quiet-window median, band max(1.0 °C, 3 SD), S7 = min(300 s, 3 × peak-to-band recovery)) for that verification. Its reference is the median of the 300 s quiet window before prefill, not the soak, because the soak journal holds only R0's keys: ACCEPTED by the lead (LEAD-RULINGS-2 R6-4) and recorded in `thermometry.D.s7_for_r1_picks.reference_rule`. When R1 changed the picks, the kit binds W1's `turn_cap_s` to `s7_for_r1_picks.S7` and `delta_slow_c` to `s7_for_r1_picks.band_c.s_slow` (or a lead `s6_tuning` receipt from that base, ≤ 2.0 °C), admitting the R1-pick values and refusing the R0-pick slots S6/S7, and requires the policy's sensor keys to be `s7_for_r1_picks.keys` (protocol v4 :247-251, R6-4). `inputs.R1.thermal_policy.classification_sha256` must equal `thermometry.D.classification_sha256` (protocol WP16, R6-5); it is an inputs-level binding, stripped before the gate policy is validated or installed in a member. S1-S4 stay the R0 keys' step response (R5-7).
- **Batch-window bounds (ruling 8).** A quiet segment is admitted only if its bound ends before 11:45 or starts after 13:15: 1,800 s, plus the 600 s G0 cap (R5-2 re-arms the deadman after the G0, so the member bound no longer contains it), plus, for the 30B and D steps, the 300 s quiet and the 600 s recovery (3,300 s), and for the designed start states the 900 s preheat cap (3,300 s), plus 600 s when a release precedes it (round-5 executing review).
- **Gated runs (R6-1, superseding R5-1's cool-to-band).** The duty bar reproduces W1's D-after-D G0: each gated D run and X-G follows a D turn with exactly W1's inter-member schedule, the member's own configured idle (`sampling.idle_seconds` of the W1 kit config it runs, 300 s), and nothing else; they still consume the soak R (R5-1's consume role). The value is read from the W1 plan (`configs/campaigns/align_v4/night_plan.template.json` member configs, `align_v4_kit.w1_inter_member_idle_s`), never hard-coded: the driver refuses at t0, before any power-mode or runtime work, when a runtime template idles otherwise, and refuses a run that reports another `inter_member_idle_s`; `r1_slots.duty_bar.schedule` records it and the kit requires it. A run whose G0 timed out, or that followed a member which did no D work (a timed-out G0, or a released G0 with zero decode tokens; `follows_d_turn` null), is INCONCLUSIVE (recorded, never a refusal): its duty-bar row has verdict `inconclusive` and an `inconclusive_reason`, the duty bar's overall verdict is `fail` if any judged run fails, else `inconclusive` if any run is inconclusive, else `pass` (`pass` is true only for `pass`, so the kit needs a recorded lead fallback otherwise), and a replay-pair run that is inconclusive makes U5 INCONCLUSIVE with `sigma_pair_valid: false`. `r1_slots.x_g` records X-G's G0 outcome the same way (`status` `measured` or `inconclusive`). A timed-out run's G0 (its cap) stays in ruling 1(f)'s worst-case G0 term, so the kit stays conservative.
- **Calibration segments (R6-2).** Step-d and the designed start states start from a defined state (the precools above). A G0 timeout there is retried once after another precool (`<name>.precool_retry`); a second timeout records the segment in `r1_slots.inconclusive_segments` and R1 continues (fail closed at the kit, not mid-night). An INCONCLUSIVE step-d leaves no slots, so the gated D runs and X-G are not run (`skipped_segments`; a gated run never runs unbudgeted, R5-4), the thermometry bar is `inconclusive` and the kit refuses W1 naming step-d. An INCONCLUSIVE designed start state gives β_T no point: `planning_temperature.status` is `inconclusive` and so is U5. The kit refuses W1 for any entry in `inconclusive_segments` (step-d by name), so the lead rules before W1 (fail closed at the kit).
- **S6 (R5-7).** S6 = δ_slow (S5) until the FD 2.6 tuning. `r1_slots.s6_tuning` records the TODO with the gated runs' median G1 and hold waits (`gate_waits_s`), the input the lead tunes S6 on.
- **A-B-A (ruling 16).** The sequence for each leg:
  1. The driver sets the mode with the narrow sudo rule and reads it back.
  2. It waits outside 11:45-13:15 local (ruling 8).
  3. It runs `g0-release-soak`, then the leg.

  A leg is redone, after another release, on sustained load. If any accepted leg's release timed out (`released: false`), or a leg's own G0 did not release (`g0_released: false`, R5-3), adoption is INCONCLUSIVE, the series stays Automatic and R1 continues; the ruling 16 rule is then `not_evaluated` when a leg has no t_decline. Both A legs infinite with a finite B is not adopted (ruling 16). The batch-window wait for a leg uses its bound from the configured values (round-3 LOW-1): 65 s pre-roll + the 600 s G0 cap + 1,750 s (the largest member intercept I_D the runtime admits; the legs run before step-d, R5-5, so step-d's I_D is not yet known) + 1.13544 × the runtime config's `step.deadman_s` + 120 s.
- **Duty bar and L1 (ruling 1(d), lead ruling L1; executing review MEDIUM-2).** On the R1 record the driver computes L1 T_dead = min((1750 − I_D)/1.13544, (1800 − I_D − max_tail − 10)/1.13544) from the step-d `I_D` and the largest gated-run tail, prints it (`R1 L1: {...}` on stdout) and stores it as `l1` in r1_slots with the member fit I_D + 1.13544·T_dead + tail + 10 for the armed and the effective T_dead. The 40 % G0 + G1 + H share is judged against min(armed T_dead, L1), the value W1 will arm.
- **Ruling 20 (external volumes).** The driver takes a volume census (`/sbin/mount` plus `diskutil info -plist`, through `joulewise/align/apple/external_volume.py` pinned to status `off`) at t0, before every runtime invocation and before it writes r1_slots, and refuses R1 if any external volume is mounted. It records every census in `r1_result.json` and r1_slots (`external_volumes`) and takes a last, recorded-only census in the terminal record.
- **Ruling 7.** Each ALIGN episode bundle records `hardware.ac_powermode = {value, source, observed_at: "episode_start"}`.
  - The value is read through `EpisodeRuntimeAdapter.powermode_reader`. `ThermalRegistry(powermode_reader=...)` binds it, and a real run defaults to a read-only `pmset -g custom`.
  - The v4 desk compares every member's recorded value with the frozen series value, using `validate_powermode_members`. Any mismatch, or an unobserved value, sets the `ac_powermode_members` check false, so `instrument_ok` is false.

- **Ruling 1(f) (lead rulings R5-4, R6-3).** r1_slots carries `budget_fit_inputs`: step-d's measured rate (`r_decode_step_d_tok_per_s`), each gated run's observed rate (`r_decode_gated_tok_per_s`: `decode_tokens` / `phases_s.decode`, null for a run that decoded nothing), their minimum `r_decode_tok_per_s` (the rate the worst case uses, R6-3; the kit re-derives it from the step-d rate and the `deadman_budget` rows' `decode_tokens` and refuses a recorded value that differs), and the gated runs' `turn_cap_tokens`, which must equal the per-turn cap of the W1 D members (anchor 1's `max_tokens`, 4,096). `deadman_budget` must hold exactly the three gated runs, each with finite, non-negative phases. The kit asserts, for the frozen `inputs.R1.B_D` and `T_dead`, max G0 + max (G1 + H) + max (prefill + tool) over the gated runs + (B_D + turn_cap_tokens)/r_decode ≤ T_dead (an admitted last turn keeps its full cap, FD:263), and prints the largest fitting B_D when it refuses. The last admitted turn keeps the full 4,096-token turn cap (conservative, R6-3); when 1(f) does not fit, the kit keeps refusing W1 and names the largest fitting B_D, and ruling 1(e)'s fallback is the lead's after the R1 night (no code fallback). It also requires `inputs.R1.B_D` ≤ `slots.B_D` and the thermal policy's `chunk_tokens` = `N_chunk`, `delta_slow_c` = `S6` (= `S5` unless r1_slots records a lead `s6_tuning` {authority, from_c = S5, to_c = S6}, with S6 ≤ 2.0 °C, ruling 1(e)) and `turn_cap_s` = `S7`.

## Host-level power-mode admission (executing review HIGH-3)

`run_night` refuses every plan class (`night_refused_ac_powermode`) unless the AC-profile `powermode` read from `pmset -g custom` equals the plan's optional `ac_powermode` (0 or 2; absent means 0). A High Power marker means a restore to Automatic is owed. There are two: the host-level marker (lead ruling R6-7, below) and the R1 chain's own `$MEASUREMENT_ROOT/.align-r1-high-power`. Under a plan that expects 0, if either exists, admission first runs the narrow `sudo -n /usr/bin/pmset -c powermode 0`, reads the mode again and removes the markers only once that read is 0; it never restores while another process holds the host night lock (it refuses instead). A failed read is retried once. The v4 session `install` (W1/D arm) applies the same admission against the kit's frozen series value and writes `staging/v4-arm-NNN.json` with the observed value, the exact pmset text and the ruling 20 volume census, admitted or not.

**Host-level marker and night lock (lead ruling R6-7).** The marker lives at one host-level path that every session, night, the R1 driver and the watchdog see, outside any per-session measurement view: `$JOULEWISE_HOST_STATE_DIR/high-power.marker`, default `/Users/Shared/JouleWise/host-power/high-power.marker` (user-owned; the narrow sudo rule is not needed for it, and tests and synthetic harnesses always set the variable). Its first line is the tag (`ALIGN v4 W1 high-power restoration required` for a W1 session, `high-power restoration required` for the R1 driver), its second the owner as JSON (the W1 session's `custody_root` and `plan_path`). Beside it, `night.lock` is the host night lock: an exclusive `flock` that a measuring night holds for as long as it measures (a night admitted under a declared 2, from before its admission read to the end of its close; the R1 driver for its whole run; a v4 `install` for its whole arm). The R1 driver restores Automatic at its teardown only while it holds the lock (a run refused before taking it never changed the mode). Test modules that reach these paths point `JOULEWISE_HOST_STATE_DIR` at a temporary directory (the `tests.align` package does it for every ALIGN test). The kernel drops it when the holder dies, SIGKILL and power loss included, so it never outlives its night. **No restore ever runs while another process holds the lock**, so neither a late launchd fire of a released plan nor an operator's session start can change the mode under a measuring night.

**W1 under an adopted High Power (lead rulings R5-6, R6-7).** When r1_slots freezes `ac_powermode` 2:
1. `align_v4_session.py prepare` writes `ac_powermode: 2` into the night plan (the b5 window plan writer's optional `ac_powermode` input).
2. `install` takes the host night lock (refusing if a night holds it), restores any marker it does not own (session start, below), writes the host-level W1 marker naming this session, then sets `sudo -n /usr/bin/pmset -c powermode 2` (the same narrow rule), reads it back and runs the arm admission against 2. If the arm then refuses for any reason, or the shared installer returns without installing (launchd already holds a night job; round-5 cold pass MEDIUM-1), it restores Automatic (`staging/v4-arm-restore-*.json`) and raises. `install` refuses a terminal session and does not set the mode again for an installed one.
3. `run_night` admits 2 only for a plan that declares 2, holding the host night lock from before its admission read; with that plan a W1 marker owned by this night's session (same custody root or plan path) is the night's own and is kept, with no restore at admission. Any other marker (an R1 crash, another session's W1 marker) is a restore owed: it is restored first, as under a plan of 0, and the night then refuses on the mode. A night admitted at 2 with no marker writes one it owns before it measures, so its own SIGKILL still leaves a host-level obligation. Markers are removed only after a restore reads back 0.
4. When that night closes, on every exit path, `run_night` restores Automatic, reads it back, removes the markers only once it reads 0 (logged as `ac powermode close`) and then releases the lock. A failure or interrupt in the close never replaces the night's own exit code.

**Every non-measuring exit restores (R6-7).**
- **Admission refusal** of a night declaring 2 (a mode mismatch, or a failed `pmset` read twice): restore Automatic and clear the markers while holding the lock, then release it.
- **Malformed plan, rerun record, J4 `launch_abandoned.json`**: `run_night` restores the host-level W1 marker this plan owns (same custody root, or the same plan path when the plan does not parse), taking the lock without waiting. It leaves alone a marker another session owns (a retried night's) and any marker while a night holds the lock (logged `ac powermode exit restore`).
- **Never launched**: the watchdog's J4 release (no driver record by t0 + 900 s) restores the marker that plan owns, under the same two rules (`high_power_restore` event); the retry's own `install` re-enters High Power.
- **Session start**: `prepare` and `install` restore any marker the session does not own (an R1 crash, a killed or abandoned W1 night), then read the mode back; a restore that fails refuses the session, and a night holding the lock defers it to that night's close.
- **Every later admission** (any plan class, any measurement root) sees the host-level marker, so a W1 night that dies without its close (SIGKILL of `run_night` itself, power loss) is restored by the next session start or night admission. A failed close restore keeps the marker, and that next admission retries it.

## Re-runs

A re-run into an existing `<NIGHT_DIR>/align-r1` refuses (exit 3) without a traceback and never overwrites an earlier `r1_result.json`; if the directory holds none (a SIGKILLed run), the refusal is written there.

## The WP15 runtime (`joulewise/align/apple/r1_runtime.py`)

The runtime adds orchestration only; every measurement uses an existing production path:

- **Model segments** (`step-30b`, `step-d`, the planning turns, the A-B-A legs, `x-g`, the gated D runs, `d-4bit`) run `run_benchmark` with a `ThermalRegistry`: the ALIGN episode adapter, `MlxEndpoint` on mlx_lm, `ThermalSession` (SMC sidecar, G0/G1/H, the powermetrics status tap), the episode deadman, the powermetrics telemetry adapter, the bundle custody writer and the ruling 7 powermode record. Members are built from the generated kit configs named in `configs/align/v4/r1_runtime.json`, tagged `align-v4-r1`/`non-claim` without launch lineage. Bundles land in `DIR/runs/`.
- **Step tests** (10k fed prefill + 4,096 seeded decode) are one-turn episodes of a deterministic long-prefill task (`StepTask`), gated by a G0 against the soak R with no G1 or holds so the decode is continuous. For `step-30b` and `step-d` the G0 runs on its own 600 s cap, a released G0 is followed by 300 s of quiet, and only then is the step deadman armed, for the decode (`token_budget.deadline_origin` = `R1_after_G0_release_and_quiet`).
- **Designed start states** keep the preheat (900 s) and G0 (600 s) caps of their own; the deadman is armed after them, for the decode only (`deadline_origin` = `R1_after_preheat_and_G0`; LEAD-RULINGS-2 R5-2).
- **Sensor segments** (`idle`, `idle-until-soak`, `g0-release-soak`) run a `ThermalSession` alone in `DIR/<label>/align_thermal.jsonl`; `g0-release-soak` starts powermetrics for the PM state, pre-rolls 65 s for the slope window and calls the production `wait('G0')` with R as its reference.
- **Read-back** uses `read_episode_bundle`, `thermal_desk.read_bundle_record` (`energy_j` is its `turn_owned_j`), `thermal_desk.native_pm_samples` (the PM clock) and `attribute_episode` (decode energy).
- **Completeness** (round-4 executing review HIGH-1, Fable cold pass HIGH-1; for step-d and the designed start states a pure G0 timeout is the INCONCLUSIVE result instead, LEAD-RULINGS-2 R6-2): a step (`step-30b`, `step-d`, `d-4bit`), planning-turn or A-B-A member must be exactly one turn, `succeeded`, with none of `episode.deadman:`, `episode.decode_budget:`, `episode.g0_unreleased:`, `episode.time_guard:`, `episode.context_limit:`, `episode_error:`, `endpoint_error:`, `thermal.start_gate_timeout`, `thermal.gate_timeout:`, `thermal.hold_timeout:`, `thermal.state_unobserved`, `thermal.collector_failed`, `thermal.custody_invalid` or `thermal.status_source_missing` (`r1_runtime.INCOMPLETE_MEMBER_FLAGS`); otherwise the runtime exits 3 and R1 refuses. A malformed or refused tool-call flag does not cut the decode and does not count. The gated D runs and X-G are exempt: their truncation is the duty-bar evidence.
- **Journals**: `contract.LoadJournal` once a second (the runtime's own PID tree excluded) and `pmset -g batt` every 30 s (`DIR/battery.jsonl`).

Field derivations and their stated approximations:

`r1_slots.slots.S5_fast` records S5's fast twin, the soak-derived `delta_fast_c = max(1.0 °C, 3 × SD_fast)`, and W1's `thermal_policy.delta_fast_c` must equal it when R1 keeps R0's picks. When R1 changes the picks (R6-4), `S5_fast` still describes R0's fast key, so `thermal_policy.delta_fast_c` must instead equal the fast band computed for the R1 picks, `thermometry.D.s7_for_r1_picks.band_c.s_fast` (quiet-window form, like S6/S7; round-6 integration).

- `sensor_series_c` / `sensor_series_t_s`: the valid 1 Hz reads of the R0 gate keys in order, with each read's time in seconds from the first journal row; a failed read is dropped, never interpolated.
- `recovery_curve`: `[t_s, S_slow]` per read until |S_slow − R| ≤ δ_slow, or the cap.
- `deadman.phases_s`: G0/G1/H from the episode's `ThermalSession.record()` intervals; prefill (turn start to first token), decode (first token to turn end, holds removed) and tool time from the episode; tail = episode end past the G0-entry deadline.
- `slots` (step-d): S1/S2 = fast-key ΔT and t63 (with no rise t63 is null and flagged `t63_censored`, never 0.0, so the driver refuses at step-d: R1's thermometry bar fails; executing review round 4 LOW-9); S3/S4 = slow-key ΔT and cooling τ (key names and the FD 2.6 class checks are in `slot_detail`); S5 = δ_slow = max(1.0 °C, 3 × soak SD); S6 = the δ_slow the R1 gates use (TODO: the FD 2.6 S6 tuning, tied to the gated runs' median G1 wait, R5-7); S7 = G_turn = min(300 s, 3 × the recovery from the step peak to within δ of R, observed for a fixed 600 s after the last decode); S8 = N_chunk; S9 = t_decline (FD 2.6; when no decline occurs it is censored at the observed decode length and N_chunk = 2,048, A1 A3.1; no PM clock support refuses); I_D = member wall − (episode end − G0 entry); B_D = 1024 × ⌊((1800 − I_D)/1.13544 − prefill_s) × r_decode / 1024⌋, ≤ 40,960; T_dead = (1750 − I_D)/1.13544 (L1's first term; the kit applies the tail); class = D's protocol class (A1 A3.1), with the FD 2.5 rule recorded beside it.
- `e_D_j_per_token`: decode-segment energy over decode tokens of the step-d episode.
- Designed start states (planning kinds): a proportional MLX heater (`ProcessHeater`, a child process) preheats to R + offset and holds S_slow there during the production G0, whose reference is R + offset on S_slow (S_fast is not banded); it stops before the episode starts. `g0_release_c` is the G0 interval's measured release.
- `released`: the G0 outcome. `t_decline_s`: the step's t_decline, null when no decline occurred.
- `calibration-pre`/`-post` record the read-only host snapshot at the brackets; the meter calibration itself belongs to the R1 night plan's scaffold. `harvest` writes `DIR/harvest_manifest.json` (SHA-256 of every file under the R1 output) and aggregates the charge-resume events.

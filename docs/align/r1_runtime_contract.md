# ALIGN v4 R1 runtime contract (WP15 seam)

The R1 driver (`scripts/align_r1_rehearsal.py`) does no model, SMC or gate work itself. For each segment it runs the WP15 runtime argv once:

    <runtime...> --r1-kind KIND --output DIR [--duration-s N] [--soak-reference FILE]

It then reads one JSON object from stdout. A non-zero exit, a result that is not JSON, or a missing field refuses R1 (exit 3). The Automatic power mode is still restored.

The runtime argv is the list `inputs.WP15.runtime_entrypoint` in `configs/campaigns/align_v4/registration/inputs.json` (Fable cold pass LOW-3):

    ["scripts/align_r1_runtime.py", "--config", "configs/align/v4/r1_runtime.json"]

Element 0 is a repo-relative Python script; the chain passes `--runtime-entrypoint <inputs.json>` and the driver runs it with its own interpreter (`$PY -B`, the pinned venv), followed by the remaining elements verbatim. `ALIGN_R1_RUNTIME`, if set, overrides the list with one operator-pinned executable path (never shell text); this is the only place the override is defined.

The field table lives in `joulewise/align/apple/r1_runtime_contract.py` (`KIND_FIELDS`, `QUIET_FIELDS`, `NEEDS_SOAK_REFERENCE`). The driver checks every result against it at the seam. This document is the prose form of that table, and a test keeps the two in step.

The production driver requires `--prepare-packet FILE` from
`align_r1_followup_kit.py prepare` (the chain receives `ALIGN_R1_PREPARE_PACKET`).
Before acquiring the host lock it checks `FOR_LEAD_ARM`, the current
`executed_commit`, the bound source hashes, and both RL-62/73 checks (`weight_digests`
and `runtime_stack`, each `ok: true`). Its arm record carries the packet path,
SHA-256 and both results. A missing, stale or refused packet is a named refusal.
The synthetic driver remains fixture-only.

**Arm step for the packet (Fable kit delta review D-7, procedural route; no code change).** The driver
refuses a packet from another commit or with other source hashes, but accepts any packet left at the fixed
path by an earlier night of the same commit: the packet carries no plan, night or date. So every arm of an R1
night does, in this order, on the measurement Mac from the final commit:

1. delete any existing `$MEASUREMENT_ROOT/.align-r1-prepare.json` (`prepare` opens it with mode `x` and
   refuses an existing file, so this step is what makes the packet fresh);
2. run `align_r1_followup_kit.py prepare` on the final commit with the real weight-digest and
   installed-stack preflights, and record the SHA-256 it reports, in the arm notice;
3. arm; after the arm, compare the arm record's packet SHA-256 with the SHA-256 recorded in step 2. A
   mismatch is a refused arm: uninstall and repeat from step 1.

The check is procedural because the driver (`scripts/align_r1_rehearsal.py`) is a condition-13 file; moving
the packet into the night's output directory in code would repeat the smoke.

`capture-predecessor-30b` is the ordinary 30B capture predecessor introduced by
`a85ee8ec6` for RL-72's indivisible predecessor/step-D admission unit.
Its runtime fields remain defined by `KIND_FIELDS`.

Smoke Part B's post-G0 engineering watchdog is the sum of the registered quiet,
the re-armed turn deadman, recovery, and a 120 s classification/close margin
(300 + 1,580 + 600 + 120 = 2,600 s with the current config). G0 keeps its
1,200 s cap. RL-84 P-5 confirms that Part B's twenty minutes is an estimate,
not a total bound. This executed-byte engineering change requires delta
review before smoke.

Both parts admit through G0 on one engineering budget, `r1_runtime.SMOKE_ADMISSION_S`
= 3,000 s on the kit's clock (RUN_STATE 276). The 1,800 s it replaces predates
RL-84 P-1's 30B predecessor in the smoke, and smoke 276's Part A hit it 727 s
into a G0 wait. Part A must fit the predecessor (551.3 s in smoke 276), step D's
start-up to G0 entry (521.6 s; R1 night 518.1 and 516.0 s), the full 1,200 s G0
cap and its close after G0 (R1 night at most 134.6 s): 2,407.5 s, plus 592.5 s of
slack. The runtime's pre-G0 itimer, its G0-return check and the kit's two Part A
checks read the constant, and the launcher's caps derive from it: A = 3,000 + 120
= 3,120 s, B = 3,000 + 2,600 + 120 = 5,720 s, and the launch minimum is
3,120 + 5,720 + 300 + 2 x 180 + 10 = 9,510 s. RL-84 P-5 rules only the G0 cap,
so this is an engineering watchdog, not a ruled parameter. It is active only
under `--smoke-part`; no night member reads it. It changes the executed bytes
of `r1_runtime.py` (condition 13), so it gets a delta review before the smoke.

## Arguments

- `--output DIR` is always the canonical segment directory, `<R1 output>/<segment name>`. When the driver rejects an attempt (ruling 8 load, or soak slope), it renames that directory to `<segment name>.rejectedN` (the next free N from 1) before the next attempt starts. A step-d or designed start state whose G0 timed out is moved to `<segment name>.g0_timeout1` before its one retry (LEAD-RULINGS-2 R6-2). The accepted attempt therefore always ran in, and owns, the canonical directory. The runtime must write only inside `DIR` and use paths relative to it.
- `--soak-reference FILE` is passed to every invocation after the accepted idle soak. The file is `<R1 output>/soak_reference.json`, schema `joulewise.align.r1_soak_reference.v1`, and holds:
  - `sensors_c`: per sensor key, the mean over the last 1,200 s of the accepted soak. This is the reference R.
  - `detrended`: the slope, SD and mean per key.
  - the source attempt.

  Every release, the post-D cooldown, the calibration precools (R6-2), X-G, the gated D runs, the designed planning-turn start states and the A-B-A legs measure against this R. The kinds marked "R" below refuse without it. No R1 model member keeps a self-captured reference: each installs R (or its designed start state) through a session hook before warmup, so the gate policy's `capture` role never fires (LEAD-RULINGS-2 R5-1).
- `--duration-s N` is given for fixed-length idle segments only.
- The kinds that run D under the R1 slots (`x-g`, the gated D runs) read the accepted step-d result, `<R1 output>/step_D_prefill_10k_decode_4096/runtime_result.json`, for T_dead, B_D, N_chunk and G_turn. They refuse without it, and they refuse unless its bytes are the ones the step-d runtime's own `runtime_custody.json` (status `complete`) digested (Sol wp15rev F3: a post-close edit of B_D, N_chunk or T_dead is refused). Reading a sibling is the runtime's only access outside `DIR`.
- A gated D run never runs unbudgeted (lead ruling R5-4): it refuses (exit 2, before any model work) unless the step-d `B_D` is a multiple of 1,024 in [1024, 40960] and `T_dead` is finite and positive. step-d floors a small budget to 0, so the driver checks the same rule right after step-d and refuses there, before the cooldown, X-G and the gated runs; it also refuses there when any slot is not finite (a no-rise t63 is null, below).

## Signals and custody (Fable cold pass MEDIUM-1)

- On its first TERM/INT/HUP the driver sends TERM to the running runtime, waits at most 20 s (inside run_night's 30 s), and only then sends KILL. Later signals are ignored so the wait and the Automatic restore complete. Lead ruling R8-1: the driver records the runtime's descendants from the process table while the runtime lives (before the TERM, and again before a KILL); once the runtime is reaped it TERMs every one still alive with its recorded command, waits at most 5 s, KILLs, waits at most 5 s more, and proves none is left. Each proof is recorded in `r1_result.child_terminations`. A process is identified by its pid and start time (`ps … lstart`), so an exec is still tracked and a reused pid is never signalled; the tree is re-read about once a second during the grace. If a census fails, a descendant survives (a root `powermetrics` the user cannot signal), the runtime is not reaped within 30 s of its KILL, or its output pipes are still held open after the tree is ended (an unrecorded holder), the guard restores nothing (`restore_deferred` names R8-1) and the markers stay for the dead-man or the next session start. **Worst-case teardown bound (round-8 disposition D8-5, R8 exec LOW-5).** The "20 s inside run_night's 30 s" is the runtime's TERM grace only. From its first signal the driver's whole teardown is bounded by: the 20 s grace (plus at most one 5 s `ps` read that starts before the grace ends), a `ps` read of at most 5 s before the KILL, the reap of at most 30 s after the KILL (`REAP_AFTER_KILL_S`; immediate unless the KILLed runtime sits in uninterruptible I/O), `_stop_tree` (a 5 s `ps` read, then for TERM and for KILL a 5 s wait plus at most one 5 s `ps` read and a 0.1 s poll), the 5 s drain, and then the lock retake and the sudo restore with its read-back (seconds in practice, with no timeout of their own). That is about 60 s before the restore with a reaped runtime and about 90 s with an unreaped one, against run_night's 30 + 5 s (group TERM, a 30 s wait, a 5 s re-signalled group census, then the group KILL), because under run_night the zsh chain leader stays alive while its trap waits for the driver. If the driver runs past 30 + 5 s, run_night's group KILL cuts its restore and its `r1_result.json`; that fails safe: the markers stay for the next admission, the dead-man or the next session start. With the WP15 runtime the case is unlikely: its watchdog exits by 19 s, and its descendants have already received run_night's group TERM.
- On TERM the runtime must stop work and, within 20 s: let an open controller bundle salvage and finalize (that stops powermetrics and closes the bundle's SMC sidecar), close its own SMC sessions, heater and journals, write its terminal record and exit 128 + signal. The WP15 runtime forces its own exit after 15 s.
- Around a managed session close on the main thread, TERM/INT/HUP are deferred until the close returns or at most 10 s after the first held signal (R6-8 exec LOW-3, bounded by R7-8). At that bound, held signals reach the previous handlers on the main thread even if the close is blocked. Lead ruling R8-3: the runtime's 15 s teardown watchdog is armed when the first signal is held, not when the deferral ends, so the forced exit (15 s, plus at most 4 s of hard-exit teardown) always lands inside the driver's 20 s grace. A failed close stays retryable; off-main-thread closes run without deferral.
- The terminal record is `DIR/runtime_custody.json` (`status`: `complete`, `refused`, `failed` or `aborted`, the signal, and the SHA-256 of every other file in `DIR`; a file of the same name below `DIR` is digested like any other, Sol wp15rev F2). It is written last on every exit path. On the 15 s watchdog path (executing review round 4 LOW-1) the runtime first sends TERM to every `powermetrics` process in its own process tree (the `sudo` child relays it to the root `powermetrics`), then writes the record with `status: aborted`, `watchdog: true` and the pids it signalled; digests that would run past a 1.5 s deadline (checked per 1 MiB block) are listed as `unhashed: watchdog deadline`. A pid is signalled only if a second process snapshot still shows it in the runtime's tree with the same parent and command. One writer owns the terminal record: if the watchdog publishes, the normal path never replaces it, and the watchdog never overwrites a normal record. An independent hard exit 4 s after the watchdog fires bounds even a stalled teardown, so the forced exit stays inside the driver's 20 s grace. A teardown that a first signal interrupts still closes every remaining session (the powermetrics stop included) and the load journal (Sol wp15rev triage). After an abort `DIR` is incomplete: it holds the salvaged bundle and journals, and the custody record says so. Nothing is printed on stdout unless the segment completed.
- The runtime refuses (exit 2) when `DIR` already exists, an input is PENDING (R0 sensor keys, the kit's R0 reasoning effort, WP18's X-G turn count, the D-4bit source) or `--soak-reference` is missing or unreadable; it exits 3 when the segment ran but cannot supply its fields.

## Fields every quiet segment returns (council ruling 8)

The quiet segments are:
- the idle soak;
- the 30B and D step tests;
- the three planning-turn states;
- the three A-B-A legs.

Each returns:

| field | type | meaning |
|---|---|---|
| `cpu_busy_cores` | list of finite numbers, 1 per second | Background CPU load in cores: summed %CPU / 100 of every process outside the measured runtime's own process tree. The driver redoes the segment when the load is > 0.5 core for 60 consecutive seconds. |
| `cpu_busy_t_s` | list of finite numbers, same length | The time of each `cpu_busy_cores` sample in seconds on the segment's own clock (nondecreasing). |
| `census` | non-empty list | Process census: the full process table at least at segment start and end. |

The journal must cover the segment (executing review MEDIUM-1). With W the wall seconds the driver measured around the invocation, R1 refuses unless there are at least 0.9·W − 5 samples and no two consecutive sample times are more than 5 s apart. Without that, one sample could stand for an 1,800 s soak and the 60 s-sustained rule would be vacuous.

`LoadJournal` in the contract module is the reference implementation of these fields. Each ruling 20 census retries one failed `diskutil info` per mount before it counts the mount as unmeasured (executing review round 4 LOW-3); the failure stays on the record (`diskutil_failures`). It uses `ps -A -o pid=,ppid=,pcpu=,comm=` and excludes the runtime's PID tree. A redo of a heavy segment starts only after a `g0-release-soak` release, never straight after the contaminated attempt.

## How the driver uses the fields

- **U5 (ruling 6 with lead ruling L2, c = 1.0).** Inputs:
  - σ_pair = max(|E_a − E_b|, 2.97 J), where E_a and E_b are the `energy_j` of the two spam/benign replay runs;
  - δ_slow is the planning-turn `delta_slow_c`.
  - a replay run that admitted no turn (its G0 did not release, so `energy_j` is 0) makes |E_a − E_b| meaningless; U5 is then INCONCLUSIVE with `sigma_pair_valid: false` and the reason (round-4 executing review HIGH-2).

  The verdict:
  - PASS if |β_T|₉₀·δ_slow ≤ σ_pair;
  - FAIL if |β_T|·δ_slow > σ_pair;
  - INCONCLUSIVE otherwise.
- **Order (LEAD-RULINGS-2).** calibration-pre, idle soak, 30B step (no separate cooldown after it: R6-6), the A-B-A legs, then **under the adopted series mode** (High Power if A-B-A adopts, else Automatic; protocol v4 :243-251, R5-5): the step-d precool, step-d, the post-D cooldown (ruling 1(c)), the designed start states **warmest first** (R + 4, R + 2, R + 0 °C, R5-2), each after a precool to the G0 band of R (the post-D cooldown for R + 4; R6-2), then the three gated D runs and X-G back to back in the order **D_bank, D_spam a, D_spam b, X-G** (R6-1 and LEAD-RULINGS-2 R7-1: the R + 0 °C planning turn is the D turn before D_bank, so both runs of the U5 replay pair follow a full gated D episode with the same idle, matched predecessors as in CHAIR 1(g); X-G follows D_spam b, W1's D → X transition), the optional 4-bit, then Automatic is restored before calibration-post and the harvest. Each A-B-A leg must record its leg mode, and each model member after the decision the series mode, as an observed integer (ruling 7; an unobserved value refuses R1); `r1_slots.slots_ac_powermode` records it and the kit requires it to equal `ac_powermode`.
- **Thermometry bar (protocol v4 :243-251, R5-5).** Around both planning-turn steps (30B and D) the runtime journals every inventoried `T*`/`F*` key at 1 Hz (`DIR/inventory/inventory_journal.jsonl`) from before the member through a fixed 600 s recovery; the step member idles 300 s after its G0 release, so the last 300 s before prefill are quiet. The WP14(a) classifier (`smc_enumeration.rank`, stage `r1`) runs on idle = the 300 s before prefill dispatch, load = prefill dispatch to the last decode, recovery = 600 s. The D classification fills `r1_slots.thermometry` (`bar`: pass only with both picks, and `fail` with `r1.picks_aliased` and a `bar_reason` when the two picks are one key or sit in one of the classification's `alias_groups`, LEAD-RULINGS-2 R8-6; `r1.sensor_pick_changed` when a pick differs from R0's); the 30B one is recorded only. The kit refuses W1 unless the bar passed, unless W1's gate keys (`R1.thermal_policy.sensors`) are in the D classification's die and heatsink lists, and, when R1 changed (or did not report) R0's picks, unless the lead recorded `thermometry.lead_verification`. For changed picks the runtime also computes `thermometry.s7_for_r1_picks` from the inventory journal (reference = the median of the last 60 s of the quiet window, band max(1.0 °C, 3 × that window's OLS residual SD), S7 = min(300 s, 3 × peak-to-band recovery)) for that verification. Its reference comes from the 300 s quiet window before prefill, not the soak, because the soak journal holds only R0's keys: ACCEPTED by the lead (LEAD-RULINGS-2 R6-4) and recorded in `thermometry.D.s7_for_r1_picks.reference_rule`. **One baseline (LEAD-RULINGS-2 R9-2, protocol WP14(b), PR #692 D2).** That reference and band are the classifier's own D2 baseline for each pick (`r1_runtime.quiet_baseline`: the same valid reads, the last `IDLE_WINDOW_S` of the idle phase, the median and `_idle_stats`'s OLS residual SD), recorded as `reference_c` and `noise_c` with `rule` = `r1_runtime.R1_PICK_S7_RULE`. The kit re-derives `band_c` (`r1_runtime.pick_band`) and `S7` (`r1_runtime.pick_s7`) from `noise_c` and `recovery_s` and refuses a record on another rule (the pre-R9-2 whole-window median and raw SD) or with numbers that differ, so the runtime and the kit cannot disagree. When R1 changed the picks, the kit binds W1's `turn_cap_s` to `s7_for_r1_picks.S7` and `delta_slow_c` to `s7_for_r1_picks.band_c.s_slow` (or a lead `s6_tuning` receipt from that base, ≤ 2.0 °C), admitting the R1-pick values and refusing the R0-pick slots S6/S7, and requires the policy's sensor keys to be `s7_for_r1_picks.keys` (protocol v4 :247-251, R6-4). `inputs.R1.thermal_policy.classification_sha256` must equal `thermometry.D.classification_sha256` (protocol WP16, R6-5); it is an inputs-level binding, stripped before the gate policy is validated or installed in a member. S1-S4 stay the R0 keys' step response (R5-7). **Aliases (LEAD-RULINGS-2 R7-13).** The classification also records `alias_groups` (inside its digest): sorted groups of inventoried keys whose 1 Hz (value, error) series are identical in every row of the classification journal, failed reads and their errors included (keys never read are left out). Since the integration of PR #692 this is the classifier's own alias signature (`smc_enumeration.rank` `selected_key_aliases`), so a pick's alias group is exactly its `selected_key_aliases`: one alias definition. ## Host-level power-mode admission (executing review HIGH-3)

`run_night` refuses every plan class (`night_refused_ac_powermode`) unless the AC-profile `powermode` read from `pmset -g custom` equals the plan's optional `ac_powermode` (0 or 2; absent means 0). A High Power marker means a restore to Automatic is owed. There are two: the host-level marker (lead ruling R6-7, below) and the R1 chain's own `$MEASUREMENT_ROOT/.align-r1-high-power`. Under a plan that expects 0, if either exists, admission first runs the narrow `sudo -n /usr/bin/pmset -c powermode 0`, reads the mode again and removes the markers only once that read is 0; it never restores while another process holds the host night lock (it refuses instead). A failed read is retried once. The v4 session `install` (W1/D arm) applies the same admission against the kit's frozen series value and writes `staging/v4-arm-NNN.json` with the observed value, the exact pmset text and the ruling 20 volume census, admitted or not.

**Host-level marker and night lock (lead ruling R6-7).** The marker lives at one host-level path that every session, night, the R1 driver and the watchdog see, outside any per-session measurement view: `/Users/Shared/JouleWise/host-power/high-power.marker` (user-owned; the narrow sudo rule is not needed for it). Lead ruling R7-10: that directory is fixed in production. `$JOULEWISE_HOST_STATE_DIR` overrides it only as a test seam (tests and synthetic harnesses always set it); the production entry points (the `__main__` of `run_night.py`, `align_v4_session.py`, `align_r1_rehearsal.py` and `magistrate_watchdog.py`) mark themselves, and from then on any use of an overridden directory refuses (`HostStateOverrideRefused`: an admission refusal, a refused session command, an R1 exit 3, or no J4 restore). The night's admission record and custody log (`ac powermode admitted: …; host state dir …`), the arm record (`staging/v4-arm-NNN.json`), the session-start restore records and `r1_result.json` record the directory used. Its first line is the tag (`ALIGN v4 W1 high-power restoration required` for a W1 session, `high-power restoration required` for the R1 driver), its second the owner as JSON (the W1 session's `custody_root` and `plan_path`). Beside it, `night.lock` is the host night lock: an exclusive `flock` that a measuring night holds for as long as it measures (a night admitted under a declared 2, from before its admission read to the end of its close; the R1 driver for its whole run; a v4 `install` for its whole arm). The R1 driver restores Automatic at its teardown only while it holds the lock (a run refused before taking it never changed the mode). Lead ruling R7-5: the lock lives as long as the night's process tree. `run_night` hands the lock's descriptor to the chain (`pass_fds`) for a night admitted under 2, and the R1 driver hands it to every child it starts (the runtime above all); releasing only closes a descriptor, never `LOCK_UN`, so the kernel drops the lock when the last process of the tree closes it. A close (the `run_night` close, the R1 guard's teardown restore) first retakes the lock on a fresh descriptor, which proves no process of the night still holds it, and only then restores; if it cannot, it restores nothing and leaves the markers to the dead-man or the next session start (logged `ac powermode close deferred`, or `restore_deferred` in `r1_result.json`). Under the retaken lock the close also re-checks the host marker: a W1 marker another session owns (an install that ran between the release and the retake) is left alone with its mode. The descriptor is never passed on the measurement launcher's handoff slot (FD 198; it is moved first). Only the runtime itself inherits the lock from the R1 driver: the runtime's own children (heater, powermetrics) are stopped by the runtime's teardown and measure nothing. **Known gap, not fixed (lead ruling R8-2, round-7 exec MEDIUM-4, infra Sol F1):** the measuring members `run_campaign` starts below a W1 chain (`subprocess.run` and `subprocess.Popen` with the default `close_fds`) and the R1 runtime's heater and `powermetrics` children do not inherit the host night lock. After a supervisor SIGKILL (of `run_night`, the zsh chain and `run_campaign`, or of the R1 driver and its runtime) an orphan of that kind can see a session start or admission restore Automatic under it, because those test only the lock. No data is admitted in that case: the night has lost its supervisor and custody and is aborted (no terminal `result.json`; the dead-man writes `chain_alive` while the chain group lives). It is not fixed because passing the lock through `run_campaign` touches shared Block-5 code. On an interrupt rather than a SIGKILL, R8-1 (above and item 4 below) terminates the chain's process group and proves that group gone before any restore. **The proof covers the chain's process group, not every process of the night (round-8 disposition D8-5, R8 exec LOW-4).** The group contains every `run_campaign` member, because members are started without a new session. A process in a member's tree that starts its own session (the repository has such spawns: `smc_enumeration.py`, `flags/collect.py`, `sampler_teardown`'s setpgid) is outside the proof: if it holds the lock the retake fails and the close defers; if it does not, it is the R8-2 class above, and its night is aborted with nothing admitted. An orphaned descendant that keeps the lock makes those restores defer and the next W1 refuse on the lock: fail closed, accepted. The R1 guard also reads `pmset -g custom` back after its restore and clears its markers only on AC powermode 0 (R7-7); otherwise it keeps them and the run refuses. Test modules that reach these paths point `JOULEWISE_HOST_STATE_DIR` at a temporary directory (the `tests.align` package does it for every ALIGN test). The kernel drops it when the holder dies, SIGKILL and power loss included, so it never outlives its night. **No restore ever runs while another process holds the lock**, so neither a late launchd fire of a released plan nor an operator's session start can change the mode under a measuring night.

When that night closes, on every exit path, `run_night` retakes the lock (R7-5, above), restores Automatic, reads it back, removes the markers only once it reads 0 (logged as `ac powermode close`) and then releases the lock. A failure or interrupt in the close never replaces the night's own exit code. SIGTERM and SIGHUP end `run_night` and `install` through that same close, like SIGINT (R7-4); once the close has begun, further TERM/HUP (and SIGINT, R8-1) are swallowed so they cannot interrupt it. **While the chain runs (lead ruling R8-1, correcting R7-4's text, which held only before the chain spawned or after it exited):** an interrupt (INT, TERM or HUP) after the chain has launched first terminates the chain's process group exactly as the window-deadline path does (TERM, a bounded wait, KILL, a re-signalled group census), proves it gone, and records `chain.exited` (or `chain.unkilled` if the proof fails) and a `chain terminated on interrupt` custody-log line; only then does the close run, which can now retake the lock and restore. If the group cannot be proven gone, the close restores nothing even if it could retake the lock (a survivor that does not hold the lock never sees a restore), frees the lock and defers to the dead-man or the next session start. **Round-8 disposition D8-2 (R8 exec MEDIUM-2):** this holds on every path whose chain termination is unproven, not only the interrupt: `_run_night` sets `_CHAIN_TERMINATION_UNPROVEN` after an unproven interrupt termination, an unproven census-abort, supervision-stop or window-deadline termination (`termination_proven` false), and an exception escaping the chain wait (which never terminated the chain); the close then logs `ac powermode close deferred … not proven gone after the …` and leaves the marker. The first TERM/HUP/INT latches the shutdown, so a second one cannot cut the termination short. **Round-8 disposition D8-1 (R8 exec MEDIUM-1):** an observation inside the chain loop (`_qualification_observe`, the TRANSACTION_PACK s1 HID observation) records its fault and re-raises `KeyboardInterrupt` and `SystemExit`, so a first signal that lands there reaches this termination instead of being swallowed while the latch swallows every later one.

**Every non-measuring exit restores (R6-7).**
- **Admission refusal** of a night declaring 2 (a mode mismatch, or a failed `pmset` read twice): restore Automatic and clear the markers while holding the lock, then release it.
- **Host lock error** (R7-11): a night declaring 2 whose lock fails for any reason other than another holder (EWOULDBLOCK after the wait, which stays `night_refused_ac_powermode`), such as an `OSError` of the lock file or a refused override, refuses with `night_refused_host_lock_error` (only EWOULDBLOCK/EAGAIN counts as another holder; EACCES and every other `flock` or lock-file error is this code) and runs the owner-scoped restore path (which, like every restore, needs the lock; an unusable lock file therefore leaves the marker for a manual restore, fail closed).
- **Exception before admission** (R7-11): any exception or signal before the night's close is registered (the initial agent census, matched by the plan path as the malformed-plan exit is; a custody-log or census write; the admission itself) runs the same restore path, under the night's own lock when it already holds it, and then frees that lock.
- **`--dry-arm`** (lead ruling R8-5, round-7 cold LOW-1): a desk control that never changes the mode. An interrupt or exception during it (its initial agent census included) only exits; it never restores an armed session's High Power.
- **Malformed plan, rerun record, J4 `launch_abandoned.json`**: `run_night` restores the host-level W1 marker this plan owns (same custody root, or the same plan path when the plan does not parse), taking the lock without waiting. It leaves alone a marker another session owns (a retried night's) and any marker while a night holds the lock (logged `ac powermode exit restore`).
- **Never launched**: the watchdog's J4 release (no driver record by t0 + 900 s) restores the marker that plan owns, under the same two rules (`high_power_restore` event); the retry's own `install` re-enters High Power.
- **Dead-man** (round-6 executing review): `run_night dead-man` is the night's last exit when the night job never launched (the watchdog absent, or its J4 restore deferred or failed) and when `run_night` died without its close (SIGKILL, power loss) or its close deferred because a process of the night still held the lock (R7-5). Once it has proved the chain gone (it refuses while the chain group is alive), it restores the marker this plan owns, under the same two rules (logged `ac powermode exit restore (dead_man)`).
- **Session start**: `prepare` and `install` restore any marker the session does not own (an R1 crash, a killed or abandoned W1 night), then read the mode back; a restore that fails refuses the session, and a night holding the lock defers it to that night's close.
- **Every later admission** (any plan class, any measurement root) sees the host-level marker, so a W1 night that dies without its close (SIGKILL of `run_night` itself, power loss) is restored by the next session start or night admission. A failed close restore keeps the marker, and that next admission retries it.
- **R1 chain EXIT trap** (lead ruling R7-14, round-6 exec LOW-5; left as is): the R1 chain's EXIT-trap `pmset 0` runs after the driver has released the lock. No W1 night can be measuring then: its install needs the single `com.joulewise.night` label, which the R1 night's job still holds, and both the v4 install's census (R7-6) and the shared installer refuse while it is loaded. A future multi-label installer must revisit this. **Round-8 disposition D8-4 (R8 exec LOW-1), overriding R8-1's deferral for the R1 chain:** the R1 chain's zsh EXIT trap and its INT/TERM/HUP trap (`on_signal` → `restore_automatic`) run `pmset 0` after the driver exits, with no lock and no termination proof, even when the driver deferred its restore (zsh runs a signal trap only after its foreground child exits, and `set -e` makes any non-zero driver exit reach the EXIT trap). R8-1's deferral therefore protects only against the driver's own restore. Accepted for R1: no W1 night can be measuring then under the single launchd night label (as R7-14 above), and an interrupted R1 run's data is never admitted. Must be revisited before any W1 arm under High Power.

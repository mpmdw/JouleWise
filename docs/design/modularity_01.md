# MODULARITY-01: configuration-owned campaign and analysis declarations

## Forcing problem

The measurement runtime already separates model execution from telemetry
collection, but the older floor-campaign authoring layer repeated experiment
choices in Python source. Changing a model could therefore leave an old model
tag, plan identity, or run prefix behind. The analysis layer had the inverse
problem: registry files declared the intended conditions, while Python repeated
some of those declarations and could reject a valid registry change.

The boundary is deliberate. A campaign axis is a choice that may change before
measurement and belongs in configuration. An issued claim pin, such as a
published floor rounded to six decimal places or a lead-verified digest, is an
authentication fact and remains a literal check in its owning tool.

## Options considered

1. Add command-line flags for each axis. This avoids editing Python, but spreads
   one campaign identity over a long invocation that is easy to replay
   incorrectly.
2. Put the axes in one campaign-specification artifact and validate that
   artifact before writing output. This gives one reviewable input and a
   deterministic replay path.
3. Infer model tags and run identifiers from model paths. This removes fields,
   but path naming is not a stable scientific identity and differs across
   machines.

For analysis declarations, the corresponding choices were to retain Python
tuples, trust mutable registry files without authentication, or authenticate
registry bytes with a recorded SHA-256 digest. SHA-256 is the project's standard
content digest.

## Recommendation and implemented boundary

Use one validated campaign specification. It carries the model, the planned
repetition count `n`, workload profiles, comparative block pattern, suite
manifest reference, and run-ID prefix. The model tag is read from that artifact;
the plan identity is derived from the campaign, hardware, model, and revision
tags in it; every generated run ID uses its prefix. The default specification
must reproduce every existing frozen generated byte.

Use registry declarations as the only enumerators on the analysis side. The
Slice-2M condition pairs remain in their existing registry, whose exact byte
digest is embedded in each generated analysis manifest. Detection-floor
calibration scopes and allowed metric/window pairs live in a separate registry
with an adjacent SHA-256 record; the loader verifies the digest before any
declaration is returned. Structural rules remain in code: names must be
well-formed, entries must be unique, and a phase metric must declare the phase
window class.

## Worked example

The checked-in campaign specification names the Qwen2.5 model, the `p2015`
run-ID prefix, and the A/B/B/A block. A/B/B/A means that each comparative block
measures arm A, then arm B twice, then arm A again. Loading that artifact derives
the existing plan identity and produces the existing calibration plan, order
manifests, and runnable configurations byte for byte. The focused test then
copies only that specification, changes the model fields, repetition count,
prompt size, block order, suite reference, and prefix, and observes all six
changes in generated artifacts without modifying the generator.

## Deferred seams and exact dispositions

These are separate work because each changes an interface or a statistical
contract rather than campaign authoring alone. The state-kernel file is
magistrate-owned, so this implementation records the proposed rows without
editing it.

| Proposed row | Forcing problem | Recommendation | Closure evidence |
|---|---|---|---|
| `TELEMETRY-BOUNDARY-02` | Powermetrics-specific names remain outside the telemetry adapter and make another physical telemetry backend degrade to a reduced analysis path. | Inventory each reference, classify it as format parsing, physical capability, or claim policy, and move only format parsing behind the adapter. Keep measurement-boundary and claim-policy checks explicit. | A non-powermetrics fixture reaches reduction and validation without a powermetrics branch outside its adapter; preserved powermetrics fixtures remain byte-identical. |
| `EXTERNAL-DATASET-INGEST-01` | Workload suites are locally authored; there is no governed path from an external dataset record to a frozen prompt subset. | Add a license- and provenance-bearing import manifest, deterministic subset selection, and content hashes before adding a named dataset. | A fixture import reproduces identical prompt bytes and refuses a source, license, selection rule, or digest change. |
| `PROMPT-RENDERING-SEAM-01` | Chat-template and thinking-mode behavior is implicit in the runtime, so a model-family swap can change realized prompts without a first-class record. | Add a runtime-owned prompt-realization capability that emits the template identity, thinking-mode setting, and realized-token digest through a runtime-neutral provenance record. | Two fixture runtimes render through the same controller path; a template or mode change changes the recorded identity and a missing identity refuses claim use. |
| `BLOCK-DESIGN-REGISTRY-01` | The campaign generator now reads block order from configuration, but governed floor extraction still implements the frozen A/B/B/A estimator and its four coefficient positions directly. | Preserve the issued A/B/B/A estimator unchanged and add a registry-dispatched sibling estimator for any new coefficient vector. Do not reinterpret old artifacts under a generic formula. | Existing floor fixtures remain unchanged; a new synthetic block design is selected only by an authenticated registry declaration and fails if that declaration or coefficient vector is removed. |

The prompt-realization ownership and the statistical contract for a new block
estimator require lead rulings before implementation. The other two rows can
start with bounded inventories and contract drafts.

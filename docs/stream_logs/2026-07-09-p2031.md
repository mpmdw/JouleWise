# Live stream ledger - P2-031 token normalization and stack identity (2026-07-09)

Purpose: record shape-changing decisions for stream P2-031. This stream's
footprint is limited to `docs/contracts/token_normalization.md`, short
pointers in `docs/contracts/claims_ladder.md` and
`docs/contracts/capstone_scope.md`, and this ledger. No code or tests are in
scope.

## Entries

### P31-1 - PROMOTE-TO-DECISION-LOG - Token-normalization contract adoption

Decision: adopt `docs/contracts/token_normalization.md` as the binding home
for token-denominated metrics, cross-tokenizer comparison language, and the
reader-facing stack-identity table from 2026-07-09 onward.

Evidence:

- `docs/reviews/2026-07-09-scientific-rigor-review.md` M3 requires request
  energy as primary, tokenizer-scoped J/token, companion denominators for
  cross-tokenizer comparisons, and a stack-identity table.
- `docs/reviews/2026-07-09-scientific-rigor-review.md` Appendix B finding 6
  states that runtime-observed token denominators do not make tokens
  equivalent work across tokenizer families.
- `docs/reviews/2026-07-09-scientific-rigor-review.md` Appendix D Part C rows
  "Stack confound" and "J/token comparability" call for a stack-identity
  table and tokenizer-normalization policy.

Rationale: this is durable reader-facing claim discipline. It closes the M3
gap without moving D-037 claim-level authority or D-052 single-unit wording
out of their existing contract homes.

### P31-2 - Request energy remains the headline metric

Decision: make idle-subtracted request energy under a named measurement
boundary the PRIMARY reader-facing energy metric; token metrics remain
companions and never replace it in a headline.

Evidence:

- `docs/contracts/claims_ladder.md` already requires boundary labels and
  strict-valid evidence for result claims.
- `docs/contracts/capstone_scope.md` freezes the capstone headline as
  boundary-labeled local LLM energy characterization on named stacks.
- `docs/reviews/2026-07-09-scientific-rigor-review.md` M3 explicitly says
  request energy is primary.

Rationale: request energy preserves the measurement boundary and avoids
letting tokenizer-dependent denominators become the headline claim.

### P31-3 - Tokenizer-scoped J/token wording

Decision: allow `J/token`, `J/output-token`, and `J/prompt-token` only as
tokenizer-scoped companion metrics with runtime-observed denominators and
named tokenizer identity.

Evidence:

- `docs/decision_log.md` D-033 defines workload provenance, tokenizer
  identity/revision/class/vocab size, and the
  `joulewise.prompt_token_ids.v1` prompt token-ID hash domain.
- `docs/contracts/run_bundle_layout.md` defines the suite rollup token-ID
  hash domain `joulewise.suite_prompt_token_ids.v1`.
- `docs/decision_log.md` D-037 and `docs/contracts/claims_ladder.md` require
  runtime-observed output token counts, stop reason, and output policy for
  per-output-token claims.

Rationale: the existing provenance rules already identify realized token
streams. The new contract uses that evidence surface while making the
language limit explicit.

### P31-4 - Cross-tokenizer rankings require companion denominators or no ranking

Decision: cross-tokenizer or cross-model-family comparisons must carry
tokenizer-independent companion denominators such as `J/char`, `J/byte`, or
semantic-matched pair denominators, or remain descriptive with no
efficiency-ranking language.

Evidence:

- `docs/reviews/2026-07-09-scientific-rigor-review.md` Appendix B finding 6
  gives the failure case where lower `J/token` hides higher character- or
  semantic-item energy.
- `docs/reviews/2026-07-09-scientific-rigor-review.md` Appendix D attack 6
  says tokens are not common physical units across tokenizers, prompt
  sources, BOS handling, stop policies, and output caps.
- `docs/decision_log.md` D-053 requires denominator provenance for
  claim-bearing analysis rows.

Rationale: cross-tokenizer token counts are tokenizer artifacts, not shared
units of useful work. Companion denominators or descriptive-only language keep
the comparison auditable.

### P31-5 - Stack identity table and caption composition

Decision: require every reader-facing figure and table to carry stack
identity fields: hardware unit, OS/version, runtime/version, known
kernel/library, model artifact hash, quantization, tokenizer identity,
sampler/output policy, measurement boundary label, and telemetry backend.

Evidence:

- `docs/reviews/2026-07-09-scientific-rigor-review.md` Appendix D Part C row
  "Stack confound" requires runtime, kernel/library, tokenizer, model
  artifact, quantization, sampler, and batching policy in every figure.
- `docs/contracts/run_bundle_layout.md` defines where device, runtime,
  telemetry, model artifact identity, workload provenance, suite output
  policy, and token hashes live in the bundle.
- `docs/contracts/claims_ladder.md` owns boundary-label rules, and
  `docs/contracts/capstone_scope.md` owns the single-unit caption template.

Rationale: stack identity is the guard against hardware-causality overreach.
The caption rule composes with the two existing contracts instead of creating
duplicate boundary or single-unit language.

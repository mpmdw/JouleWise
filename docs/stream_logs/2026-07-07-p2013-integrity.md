## A-1 [orchestrator] Codex session batching: groups 1+2 first, in one session

- **Decision:** Batch commit groups 1 (writer safety) and 2
  (finite-number invariant) into a single Codex implementation session
  producing two atomic commits; keep later groups in separate sessions.
- **Alternatives considered:** (a) one Codex session per commit group
  (7–8 sessions); (b) one session for all 7 groups.
- **Why:** Groups 1 and 2 are small, mechanically independent, and both
  sit in writer/primitive territory with crisp pins — one session
  amortizes context-loading without blurring commit atomicity. All-in-one
  risks a single reviewable unit too large to counterreview cleanly and
  one bad thread poisoning everything.
- **Confidence:** High. Would change my mind: if the combined session
  produces interleaved or non-atomic commits, later groups go strictly
  one-per-session.
- **Binds:** Later groups are sessioned by coupling, not by count;
  suite-green-after-each-commit stays the gate regardless of batching.
- **Note (post-hoc):** Superseded in part by A-6 — the sandbox cannot
  commit, so multi-group sessions force manual working-tree splitting.

## A-2 [orchestrator] validation.py API design delegated to the implementer

- **Decision:** The exact `joulewise/validation.py` API (raise-vs-return,
  names) is Codex's call, required to be stated + justified in its final
  report; C-007 resolution 3 fixes only module existence,
  dependency-freedom, and coverage points.
- **Alternatives considered:** Orchestrator pre-specifying the signature.
- **Why:** The consensus deliberately left this open; per the
  multi-model doctrine the peer's design judgment is invited where the
  consensus leaves freedom, and the implementer sees all six call sites.
- **Confidence:** Medium-high. Would change my mind: an API that leaks
  policy (e.g. bundle-failure semantics) into the dependency-free module
  — that gets pushed back at the diff gate.
- **Binds:** The chosen API is recorded in A-4; later groups (4, 6) must
  consume it rather than invent parallel checks.

### A-4 [codex session A, transcribed by orchestrator] [type: code-shape] validation.py API: predicate + parsing converter

- **Decision:** `joulewise/validation.py` exposes two primitives:
  `is_finite_number(value) -> bool` (typed-number predicate; bool is not
  numeric) and `finite_float(value, field_name) -> float` (CSV/plist/
  string conversion, raises `ValueError` naming the field).
- **Alternatives:** Single raise-only function; single predicate with
  callers doing their own conversion.
- **Why (Codex):** Keeps the predicate use case (already-typed JSON
  numbers, e.g. event timestamps, clock durations) and the parsing use
  case (CSV/plist strings) explicit; callers wrap `ValueError` into
  their own domain errors (`BundleReadError`, `_ReduceError`,
  `SchemaError`) so no policy leaks into the dependency-free module.
- **Evidence:** Session A final message (orchestrator scratchpad
  `sessA.md`); commit `ea995e8`.
- **Confidence:** High — the diff gate confirmed no joulewise-internal
  imports and per-caller error wrapping.
- **Binds:** Groups 4 and 6 consume these primitives; no parallel
  finite-checks may be introduced.

- **Evidence:** Session A final message (`sessA.md`, sandbox error

  verified green independently (31→28→19 expected failures).
- **Confidence:** High.
- **Binds:** All future sessions in this stream: Codex prompts say "do
  not commit; leave the tree as the commit state".

### A-9 [codex session B] [type: contract] Powermetrics tail-drop diagnostics live in device metadata

- **Decision:** Record tolerated final-frame powermetrics drops as
  `metadata.device.parse_diagnostics[]` entries: raw artifact path, capture
  stage, action, frame index, byte count, SHA-256, and parser error.
- **Alternatives:** Raw sidecar note under `raw/`; top-level derived log
  artifact; controller event.
- **Why:** Device metadata is already the adapter-owned durable diagnostic
  surface and is written into immutable bundle evidence; a sidecar would blur
  raw-evidence semantics, and events describe lifecycle, not parser policy.
- **Evidence:** `tests.test_powermetrics.PowermetricsAdapterTests.test_run_bundle_metadata_records_dropped_powermetrics_tail_diagnostic`;
  `docs/contracts/run_bundle_layout.md`.
- **Confidence:** High.
- **Binds:** Raw powermetrics artifacts stay verbatim, including the tail;
  final-frame drops are non-gating diagnostics, while midstream and
  zero-complete-frame parse failures remain hard failures.

### A-10 [design round G8, adjudicated by orchestrator] [type: code-shape] Raw-to-trace strict gate design adopted

- **Decision:** Re-derivation helper (`samples_from_raw_powermetrics`-shaped)
  lives in the powermetrics adapter module; strict orchestration stays in
  `cli.py` BEFORE the D-030 re-reduction (import-cycle note holds). Comparison
  is parsed logical row equality — exact float `==` on timestamp_s/power_w,
  exact strings on source/rail, exact row count/order — never byte-exact CSV,
  never tolerances. Anchor reconstructed as
  `plist_first_timestamp_s - metadata.device.plist_anchor_offset_s`; the
  anchor is never inferred from the artifact under test. Succeeded
  powermetrics bundles missing raw plist or a finite anchor FAIL strict;
  mock bundles skip the sub-check; failed/unsupported stay strict-skipped.
  Named `strict: raw-to-trace: ...` problem strings, D-030-style row diff.
  Old bundles with a truncated tail pass iff their CSV rows equal the
  complete-frame derivation (no diagnostic required retroactively).
- **Alternatives:** Byte-exact CSV comparison (freezes incidental
  spelling); helper in cli.py (wrong owner for timestamp/rail semantics);
  tolerance-based compare (derivation is deterministic).
- **Why:** Strict proves analytical values derive from raw evidence, not
  CSV formatting trivia; adapter owns plist semantics.
- **Evidence:** Design-round out-file (orchestrator scratchpad `desG8.md`);
  orchestrator ground-check: all 6 real bundles carry finite
  `metadata.device.plist_anchor_offset_s` + `raw/powermetrics.plist`.
- **Confidence:** High. Would change: a real bundle whose stored CSV
  legitimately differs from re-derivation for a reason the design missed
  — that becomes a blocker discussion, not a tolerance.
- **Binds:** Group 8 implementation; test pins listed in the out-file.

### A-11 [design round P2-014, adjudicated by orchestrator] [type: contract] Provenance field shapes adopted

- **Decision:** (a) `summary_metrics.json` gains OPTIONAL top-level
  `summary_provenance` {summary_schema_version, reducer_id,
  reducer_version, config_schema_version}; constants beside
  SummaryMetrics/reduce_bundle; controller failure summaries carry the
  same shape; schema-required set stays `["status"]`; old bundles stay
  valid; strict compares legacy summaries by dropping additive provenance
  from the fresh reduction when the stored summary lacks it; new-producer
  tests require it for newly written summaries. (b) `metadata.json` gains
  `workload_provenance` (adapter-computed, controller-written via an
  additive RuntimeResult field): prompt block with realized token count +
  domain-separated sha256 over canonical JSON of realized prompt TOKEN
  IDS (`joulewise.prompt_token_ids.v1`, text hash supplemental),
  generator identity, tokenizer {backend, identifier, revision, class,
  vocab_size}, model {source, revision}, output_policy actually applied
  (name, requested/emitted tokens, stop condition). Per-bundle (= per
  repetition, D-005); campaign sameness = cross-bundle hash equality;
  `run_campaign.py` needs no changes (shells `joulewise run`). Mock runs
  emit deterministic token IDs + mock tokenizer identity.
- **Alternatives:** text-only hash (misses tokenizer drift — the exact
  risk); separate summary_metrics.v2.json (breaks D-011/D-028 canonical
  summary); controller-computed provenance (adapter is where token IDs
  become the generation input).
- **Why:** Token-id hash pins realized content identity under config-hash
  stability; single summary shape keeps readers simple.
- **Orchestrator note:** reducer_id/reducer_version on controller-written
  FAILURE summaries is a slight semantic stretch (not reducer-derived);
  accepted for shape uniformity — the fields state the contract version
  it was produced under.
- **Evidence:** Design-round out-file (orchestrator scratchpad
  `desP14.md`).
- **Confidence:** Medium-high. Would change: P2-014 implementation
  finding RuntimeResult cannot carry the block additively.
- **Binds:** P2-014 implementation session; the decision-log entries for
  provenance and phase_energy_j land with that commit (A-7, A-8).

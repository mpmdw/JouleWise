# P2-028 response-hash determinism gate ledger (2026-07-11)

## P2028-1 — CLI surface and fail-closed evidence profiles

- Status: accepted for implementation.
- Scope: public invocation surface, verdict vocabulary, configuration identity,
  and response-hash evidence sources.

Decision:

1. Ship the gate as the repo-native `joulewise determinism-gate` verb, backed
   by a stdlib-only `joulewise.determinism_gate` module. With no `--output` it
   emits verdict JSON on stdout; with `--output` it writes the JSON artifact
   and emits one summary line. Exit codes follow `envelope-gate`: 0 supported,
   2 refused input, 3 measured violation.
2. Emit `determinism_supported`,
   `determinism_violated(response_hash_mismatch)`, or `bundle_refused` with
   explicit sorted reason codes. A violation names every mismatching item and
   records each member's observed hash.
3. Establish same-config identity only after `BenchmarkConfig` validation, but
   compare the parsed raw config mappings after removing only their
   per-repetition `run_id`. Retaining unknown fields makes a future/injected
   config difference a refusal instead of silently normalizing it away.
   Require one `<experiment_id>__rN` group with distinct repetition indexes;
   neither directory co-membership nor per-member `metadata.config_sha256`
   establishes comparability.
4. Run shared strict validation first and separately require a succeeded
   summary. For suite bundles, compare lowercase 64-hex
   `outputs/suite_items.jsonl` `response_sha256` values by
   `(item_index, item_id)` so order rotation and repeated sentinel IDs are
   safe, re-derive each hash over the UTF-8 `response_text`, and require exact
   agreement with the matching `item_end` hash. Missing, malformed, stale, or
   contradictory fields refuse. For non-suite bundles, which have no
   response-hash field in their schema, hash the exact `outputs/response.txt`
   bytes as the one logical item; a missing artifact refuses.

Why this shape:

- A CLI verb composes with the existing bundle validator and gate commands,
  keeps exit/stdout behavior consistent, and avoids a second loose-script
  entry point.
- Exact typed-config comparison is stronger than a campaign-membership guess
  and intentionally does not strip descriptive config fields.
- The retained six-bundle corpus predates suite item hashes. Its auditable
  response evidence is the immutable response file, while current suite
  bundles already record per-item hashes. The two explicit profiles let the
  accepted real-corpus check remain formal without fabricating a stored field.

Alternatives rejected:

- Comparing member `config_sha256` values: each includes the distinct `__rN`
  run ID, so valid repetition groups would always refuse.
- Comparing JSONL position or `item_id` alone: suite order rotates and sentinel
  IDs may repeat.
- A suite-only gate: it would refuse all six retained strict-valid bundles and
  could not meet P2-028's existing-corpus acceptance evidence.

Evidence pointers: `joulewise/cli.py`, `joulewise/determinism_gate.py`,
`tests/test_determinism_gate.py`; retained corpus groups under `runs/` in the
primary checkout.

## P2028-2 — Conditional identity-evidence comparability

- Status: accepted by lead design ruling in the determinism-gate fix round.
- Scope: realized identity fields that must agree in addition to normalized
  configuration identity, plus legacy absence disclosure.

Decision:

1. Compare these exact current bundle fields when each field is present in
   every member: `metadata.workload_provenance.model.artifact_identity.sha256`,
   `metadata.workload_provenance.model.artifact_identity.folded_sha256`,
   `metadata.workload_provenance.tokenizer`,
   `metadata.workload_provenance.sampler`,
   `metadata.workload_provenance.generator`, and
   `metadata.environment.python_packages`. The two model hash names remain
   separate because single/mock artifacts use `sha256` while file-set model
   identities use `folded_sha256`.
2. Compare tokenizer and generator using the strict validator's required key
   projections, sampler as its complete pinned-provenance object, and package
   records using the governed `mlx`, `mlx-lm`, and `transformers`
   `present`/`version` fields. Equality is equality of canonical JSON SHA-256
   hashes, preserving JSON type distinctions.
3. Partial presence or all-present disagreement refuses with
   `identity_evidence_mismatch`. All-absent fields remain comparable for the
   allowlisted legacy corpus. Every payload records the fields proven equal in
   `identity_fields_compared` and the fields absent from every member in
   `identity_fields_absent`.

Why this shape:

- Same configured source/revision does not prove the same realized model,
  tokenizer, sampler, or runtime stack. Conditional comparison strengthens
  modern bundles without fabricating provenance for retained legacy evidence.
- The six retained bundles predate `workload_provenance` and `environment`;
  both three-member groups still return `determinism_supported` with all six
  fields honestly recorded as absent.

## P2028-3 — Per-item success is required for suite comparison

- Status: accepted after strict-validator investigation in the determinism-gate
  fix round.
- Scope: suite item eligibility for response-hash comparison.

Decision:

1. A suite item is comparison-eligible only when both its `item_end` metadata
   status and its matching `outputs/suite_items.jsonl` status are exactly
   `succeeded`. Any other or missing status refuses with
   `item_not_succeeded`; no placeholder hash is compared.
2. Bundle-level `summary_metrics.status == "succeeded"` remains necessary but
   is not sufficient for a suite comparison.

Why this shape:

- The suite contract deliberately permits `malformed`, `capped`, and
  `runtime_failed` per-item statuses while the enclosing bundle succeeds.
  A focused probe produced a strict-valid succeeded suite with one
  `runtime_failed` item whose response was the empty string and whose hash was
  the valid SHA-256 of empty bytes. Matching placeholder hashes would prove
  deterministic failure handling, not deterministic model responses.
- Checking both recorded status surfaces prevents either a failed event or a
  failed output record from entering the comparison when upstream strict
  validation has not cross-checked those two fields.

## P2028-4 — Capped completion eligibility and status-profile comparability

- Status: accepted by lead design ruling FIX-14.
- Scope: suite item comparison eligibility, sibling status comparability, and
  verdict evidence disclosure.
- Supersedes: P2028-3 Decision 1 only where it excluded `capped`; P2028-3's
  refusal rule remains binding for failure and exclusion statuses.

Decision:

1. A suite item is comparison-eligible when both its `item_end` metadata status
   and matching `outputs/suite_items.jsonl` status are in
   `{succeeded, capped}`. Missing, malformed, `runtime_failed`, `below_floor`,
   `excluded_from_claim`, and unknown statuses continue to refuse with the
   pinned `item_not_succeeded` wire reason.
2. Comparison eligibility does not erase status semantics. For every shared
   item, sibling bundles must record the same eligible status. A
   `succeeded`/`capped` flip refuses with `item_status_mismatch` and structured
   evidence naming the item and each sibling's observed status; it is not a
   response-hash violation.
3. Each bundle record exposes per-status item counts and records the status
   beside each comparison item, so all-capped and capped-heavy comparisons are
   visible in supported and refused verdict evidence.
4. The bundle-level requirement remains unchanged:
   `summary_metrics.status == "succeeded"` is necessary for comparison.

Why this shape:

- The binding capped-cell rules in `docs/contracts/analysis_plans.md` treat a
  capped cell as governed campaign evidence subject to claim-specific matching
  and exclusion rules; they do not classify capped execution as runtime
  failure. Refusing all capped items would reject designed budget-limited
  campaign completions before those rules can be applied.
- `joulewise.suite.ItemStatus` defines `CAPPED` as a first-class runtime status
  and includes it in `RUNTIME_ASSIGNABLE`. In contrast, malformed and runtime
  failure records can carry placeholder response hashes, so P2028-3's
  fail-closed rationale remains applicable to them.
- A status flip under one normalized configuration changes the completion
  semantics even when response bytes happen to match. Refusal preserves the
  evidence boundary without stretching the response-hash violation vocabulary.

Evidence pointers: `docs/contracts/analysis_plans.md` standing capped-cell
rules and AP-1/AP-2 inclusion rules; `joulewise/suite.py` `ItemStatus` and
`RUNTIME_ASSIGNABLE`; `joulewise/determinism_gate.py`; and capped/status-flip/
failure regressions in `tests/test_determinism_gate.py`.

### P2028-5 [lead+delta-audit] [code-shape] Malformed identity hashes refuse instead of comparing equal

Decision: the two hash-shaped identity fields
(`metadata.workload_provenance.model.artifact_identity.sha256` and
`.folded_sha256`) must contain valid 64-hex sha256 strings to count as
identity evidence. A present-but-malformed value in ANY sibling refuses
the group with the new reason `identity_evidence_malformed`, is excluded
from `identity_fields_compared`, is reported in the new
`identity_fields_malformed` payload array, and names the offending
bundle in `evidence_problems`. Equality of malformed values never
supports determinism (delta re-audit finding DRA-001: garbage == garbage
must not pass).

Alternatives rejected: treating malformed-equal as compared (the
audited defect); folding malformed into `identity_evidence_mismatch`
(hides the distinct failure mode from operators); validating ALL
identity fields as hashes (tokenizer/generator/package identities are
structured objects, not hashes).

Why: fail-closed evidence discipline — a malformed identity hash is
evidence-capture corruption, not comparable provenance.

Evidence: `_identity_field_classification` + `_HASH_SHAPED_IDENTITY_FIELDS`
in `joulewise/determinism_gate.py`; regressions
`test_equal_malformed_identity_hashes_are_refused` and
`test_one_malformed_identity_hash_refuses_as_malformed`. This entry also
closes the DRA-002 ledger-numbering gap (the consolidated commit body
promised P2028-1..5; this is the fifth entry).

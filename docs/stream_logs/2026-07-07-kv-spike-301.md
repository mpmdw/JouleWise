## [orchestrator] Installed-API discovery before any design

Decision: Read the actual mlx_lm 0.31.3 cache API out of the venv
(`mlx_lm.models.cache`, `mlx_lm.generate.generate_step`, `mlx_lm.cache_prompt`)
rather than trusting the plan's remembered API surface.
Alternatives considered: trust the plan's `make/save/load_prompt_cache` memory and
the `mlx_lm.cache_prompt` CLI as-is.
Why: D-015 / the spike brief explicitly warn mlx_lm APIs move; the plan's own
3.0.1 text says "verify against the installed version, do not trust this plan's
memory of the API". Confirmed surface: `make_prompt_cache(model, max_kv_size)`,
`save_prompt_cache(file, cache, metadata)`, `load_prompt_cache(file,
return_metadata)`, `trim_prompt_cache(cache, n)`, `can_trim_prompt_cache(cache)`;
`generate_step(prompt, model, *, max_tokens, prompt_cache, ...)` with a default
greedy (argmax) sampler.
Confidence: High — read from source in the exact venv the live runs use. Would
change if a different venv/mlx_lm version were used for the live run.
Binds: the spike script and all resume logic in this stream.

## [orchestrator] Fresh-process resume isolation via subprocess-per-stage

Decision: The deliverable proves cross-process replay by running monolithic,
prefill, and decode as three SEPARATE OS processes (subprocess with
`sys.executable`), passing state only through files on disk (the cache
safetensors + a `prompt_tokens.json`), never through shared Python objects.
Alternatives considered: (a) single-process demo that just re-instantiates the
model — rejected: cannot rule out lingering module/global/mx state and does not
model the real A->B node split; (b) two top-level scripts — rejected: more files,
same guarantee, worse cohesion than subcommands in one script.
Why: the spike question is specifically "resume in a FRESH process". Separate
interpreters make in-memory reuse structurally impossible; the decode process
reads the prompt token ids the prefill process persisted (it does NOT
re-tokenize), so tokenizer drift cannot confound the identity comparison either.
Confidence: High. What would change my mind: if a reviewer shows a shared-state
channel that survives process boundaries and could alter the token stream (OS
page cache / mlx on-disk cache affect only timings, not correctness).
Binds: the isolation architecture reviewers audit at the diff gate.

## [orchestrator] Resume boundary = save at full offset, trim-by-1, feed last token

Decision: Prefill with `generate_step(prompt, max_tokens=0)` (cache ends at
offset == len(prompt)); on resume, `trim_prompt_cache(cache, 1)` back to
len(prompt)-1 and feed only `prompt[-1:]` into a 64-token greedy decode.
Alternatives considered: (a) prefill `prompt[:-1]` so the saved cache already
sits at len-1 — rejected: less faithful to the canonical `mlx_lm.cache_prompt`
flow (which saves the full prompt) and pushes the off-by-one into the writer
instead of making it explicit at resume; (b) feed `prompt[-1:]` WITHOUT trimming
— WRONG: the last token is already in the saved cache, so this double-counts it
and corrupts the logits.
Why: `generate_step` prefills `prompt[:-1]` in bulk then runs a step on the last
token that ALSO advances the cache — so a `max_tokens=0` prefill leaves the FULL
prompt in the cache. Reproducing the monolithic decode boundary therefore
requires rewinding exactly one token. Verified live in-process: all 64 resumed
tokens byte-identical to the monolithic run.
Confidence: High — empirically confirmed (IDENTICAL: True). Would change if a
future mlx_lm alters the prefill/step boundary; the script asserts offsets so a
regression surfaces loudly.
Binds: the correctness claim of the whole spike.

## [orchestrator] Prompt length 1024, decode 64

Decision: Feasibility runs use a 1024-token prompt and 64 greedy decode tokens.
Alternatives considered: the plan's 512/2048/8192 sweep and 256-token decode.
Why: 3.0.1 is a feasibility spike, not a benchmark (brief: keep prompts 512-2048,
decode <=64). 1024 is a clean mid-point that gives a non-trivial cache (~28 MiB)
for a meaningful size-vs-prediction check while keeping load light; the kv-size
predictor is exercised at the same 1024 length. The full length sweep belongs to
Stage 3.4, not the feasibility verdict. The script parameterizes prompt-len so a
larger length can be re-run without code change.
Confidence: High for the feasibility purpose.
Binds: the numbers recorded in kv_feasibility.md for 3.0.1.

## [orchestrator] Verdict code derived from measured data, not hardcoded

Decision: The script computes the verdict from measured outcomes (token identity
+ cache-size tolerance) rather than asserting `replay_supported`; a regression
flips it to `partial(...)`/`replay_unsupported` with the failing reason.
Alternatives considered: hardcode the expected `replay_supported`.
Why: D-015 makes negative verdicts first-class deliverables; an honest spike must
be able to report failure. The provisional live evidence points to
`replay_supported` (identity holds, size within 0.02% of prediction), but the
recorded verdict must come from the run, not the author.
Confidence: High on the principle; the final verdict code is set from the live
fresh-process run, not this in-process probe.
Binds: the verdict recorded for 3.0.1 and the exit-checklist row.

### C-6 [codex, transcribed by orchestrator] [type: code-shape] Decode stage trusts persisted prompt ids; model path cross-checked, not re-derived

Decision: The `decode` subcommand takes the model path from
`prompt_tokens.json` (written by the prefill process) and treats a passed
`--model` only as an assertion against it; prompt ids are never re-tokenized in
the decode process. Cache-size prediction imports `joulewise.kv_size` helpers
directly instead of parsing the CLI's stdout.
Alternatives: re-tokenize in decode (rejected: tokenizer drift could confound
the identity claim); parse `kv-size` CLI output (rejected by Codex after
reading `joulewise/kv_size.py`: clean importable functions exist).
Why: keeps the token-identity comparison grounded solely in artifacts crossing
the process boundary; import beats stdout-parsing for robustness.
Evidence: `scripts/spike_mlx_prompt_cache.py` (`cmd_decode`,
`predict_cache_bytes`); Codex final messages
`docs/stream_logs/2026-07-07-kv-spike-301/codex-impl-round1.md` and
`.../codex-impl-round2.md`, incl. Codex's isolation judgment: subprocess-per-stage is airtight
against in-process reuse; residual paths (OS page cache, mmap, compiled-kernel
caches) affect timings only, not correctness.
Confidence: High.
Binds: how 3.0.1 evidence is generated; template for 3.0.2's script shape.
Depends-on: C-2 (subprocess isolation), C-3 (trim-by-1 boundary).

### C-7 [orchestrator] [type: acceptance] 3.0.1 verdict evidence = two lengths (1024, 2048), fresh-process, greedy 64

Decision: The recorded `replay_supported` verdict rests on two live
fresh-process runs (prompt 1024 and 2048, decode 64 greedy), both
token-identical with cache sizes +0.018% / +0.009% over the kv-size
prediction (~5.3 KiB constant safetensors header). The size model is declared
usable for sweep planning with a "+~5 KiB fixed" correction, no multiplicative
calibration.
Alternatives: single length (weaker scaling evidence); full 512/2048/8192
sweep (rejected: benchmarking, belongs to Stage 3.4).
Why: two lengths distinguish a constant header from a proportional error at
negligible extra cost; D-015 wants a feasibility verdict, not a dataset.
Evidence: `docs/phase_3/kv_feasibility.md` §3.0.1 (results table);
`docs/stream_logs/2026-07-07-kv-spike-301/spike_report_{1024,2048}.json`;
headline command
`.venv/bin/python3 scripts/spike_mlx_prompt_cache.py run --prompt-len 1024 --decode 64`.
Confidence: High for feasibility; timings are explicitly non-benchmark.
Binds: the 3.0.1 row in the exit checklist and 3.0.4 consolidation.

### C-8 [orchestrator, transcribing 2 lenses] [type: process] Two should-fix hardening findings — accepted, deferred, non-blocking to the verdict

Decision: Both counterreview lenses cleared the `replay_supported` verdict and
each raised exactly one `should-fix` (no blockers). Both are accepted as valid
and DEFERRED (a designed fix exists and was reverted under the session stop
order to keep the committed script coherent with the live-generated report
artifacts); neither weakens the recorded verdict.
Findings:
1. Isolation lens — `run_stage()` prepends repo root but preserves an inherited
   `PYTHONPATH`; a shadowing `mlx_lm` on the path could be imported while
   `importlib.metadata.version` still reports 0.31.3, faking the "installed
   mlx-lm" provenance. Not triggered by the recorded runs (clean repo-venv env,
   no PYTHONPATH shadow). Fix (designed): record each subprocess's resolved
   `mlx_lm.__file__` in the report and require the three stages agree.
2. Evidence lens — `verdict_for` could emit `replay_supported` on two equal
   short/empty token lists; the JSON records requested `decode_tokens: 64`, not
   observed generated counts, so the "64/64" doc claim leans on runtime
   behaviour. Not triggered (both recorded runs generated exactly 64). Fix
   (designed): derive observed counts from the recorded token lists and gate the
   verdict on `mono==resume==requested`.
Why defer not fix now: findings are robustness/evidence-provenance, not
correctness of THIS run; the stop order directed finalize-not-fix; landing the
fix cleanly requires regenerating the committed report JSONs, out of scope for
the checkpoint. Recommend folding both into the 3.0.2 shared spike-script shape
(the llama.cpp spike will reuse this harness).
Evidence: `docs/stream_logs/2026-07-07-kv-spike-301/lens-isolation.md`;
`docs/stream_logs/2026-07-07-kv-spike-301/lens-evidence.md`.
Confidence: High that neither blocks the 3.0.1 verdict; both fixes are cheap.
Binds: the 3.0.2 script-hardening backlog; does not alter the 3.0.1 verdict.
Depends-on: C-2, C-7.

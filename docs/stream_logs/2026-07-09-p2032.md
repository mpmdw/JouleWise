# Live stream ledger - P2-032 pre-hardware campaign packs (2026-07-09)

Purpose: record design decisions for the docs-only P2-032 stream. This stream
creates pre-hardware campaign packs under `docs/campaign_packs/` and does not
modify fenced files.

## Entries

### P32-1 - Scope cut-line

Decision: author only the five core hardware-gated packs named in the stream
prompt: Q1, Q2, Q3, Q6/C5-2.10, and C5-2.3. Exclude C5-2.7/2.8,
C5-3.1/3.5, and C5-I.1..C5-I.5.

Evidence:

- `TASK_QUEUE.md` row 0d lists the broader preparable set.
- `docs/research_question_registry.md` rows Q1, Q2, Q3, Q6, and C5-2.3 mark
  those rows as `pre_hardware_preparable=fully`.
- `docs/contracts/analysis_plans.md` Analysis Registry requires frozen
  contrast sets and multiplicity fields before L2/L3 claims.

Rationale: the broad interop packs invite item/source/contrast overreach until
the claims-index linter can enforce frozen contrasts and provenance. The new
directory README records this cut-line explicitly.

### P32-2 - Combined split-suite packaging

Decision: package Q1/Q2/Q3 in one split-suite file with one AP row per
question instead of three separate files.

Evidence:

- `docs/phase_3/phase_3_plan.md` Goal And Research Questions maps Q1-Q3 to
  the same split program.
- `docs/contracts/run_bundle_layout.md` Composite Split Bundles defines one
  shared composite-bundle shape for split runs.
- `docs/contracts/measurement_methodology.md` Phase Labels defines shared
  `serialize`, `transfer`, `deserialize`, and `decode` split-stage accounting.
- D-048 and D-049 in `docs/decision_log.md` bind all split questions to the
  same model-first prediction and transfer-boundary accounting.

Rationale: one pack keeps the hardware matrix, order policy, bundle layout,
and boundary labels aligned while still preserving distinct AP rows and claim
ceilings for Q1, Q2, and Q3.

### P32-3 - PROMOTE-TO-DECISION-LOG - Split transfer/deserialize floor gap

Decision: current P2-015 floor rows do not include exact floor rows for
`serialize`, `transfer`, or `deserialize` split-stage windows. The packs name
all existing exact request/prefill/decode rows they can consume and cap
standalone L2/L3 transfer/deserialize claims until P2-015 adds rows or a
frozen AP row names an accepted AP-specific bound.

Evidence:

- `docs/phase_2/detection_floor.md` Cell List includes request rows,
  `DF-PH-PREFILL`, `DF-PH-DECODE`, suite rows, and comparative ABBA rows, but
  no transfer/serialize/deserialize row.
- `docs/contracts/measurement_methodology.md` Phase Labels makes
  `serialize`, `transfer`, and `deserialize` first-class split phase names.
- D-049 in `docs/decision_log.md` requires per-cell transfer-stage boundary
  labels, making transfer energy a likely claim consumer.

Rationale: without a named same metric/window-class floor, the analysis-plan
floor gate cannot honestly unlock L2/L3 wording for those stage terms.

### P32-4 - PLANNED command labeling

Decision: runbooks distinguish current commands from PLANNED commands.
Current commands are limited to the observed CLI/scripts; transfer-bench,
split orchestration, external-meter import, composite reduction, and
KV-economics reduction are labeled PLANNED with their current owner source.

Evidence:

- `python3 -m joulewise --help` lists `validate-config`, `print-config-schema`,
  `print-output-schema`, `kv-size`, `run`, `validate-bundle`, `reduce`,
  `report`, and `envelope-gate`.
- `python3 scripts/run_campaign.py --help`,
  `python3 scripts/generate_matrix.py --help`, and
  `python3 scripts/package_bundle_pack.py --help` list the available scripts.
- `docs/phase_3/phase_3_plan.md` Stage 3.1 names `python3 -m joulewise
  transfer-bench` as future work and Stage 3.2/3.4 names split orchestration
  and matrix generation as future work.

Rationale: hardware-day docs must not imply unavailable commands already work.
Where no current TASK_QUEUE row exists for a planned command, the packs name
the phase-plan owner and state that no queue row currently exists.

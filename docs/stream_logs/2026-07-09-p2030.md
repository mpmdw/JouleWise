### P30-1 [design] Runtime order policy (spec option 2) beats per-repetition manifests

Design round: dedicated Codex session (design memo mirrored at
`.codex-bridge/last-message.md`, 2026-07-09 first invocation) argued
per-repetition manifests (Option A) vs a runtime order policy (Option B);
lead independently verified the load-bearing code facts before ratifying.

Decision: Option B, mapped to prompt_sequencing_spec sanctioned option 2 — a
real suite execution policy named in `execution_policy.order_policy`, executed
by the suite runtimes, with the realized order a pure function of
(manifest, order_policy, order_row). Option A is rejected.

Why (argument):
- D-033 pins campaign sameness as cross-bundle config-hash EQUALITY, never
  membership; D-044 puts the effective-manifest hash inside config identity.
  Option A gives every repetition a distinct effective-manifest hash, hence a
  distinct config hash — one scientific campaign fractures into B unequal
  identities, colliding with the experiment runner's `__rN` member shape
  (one config, B members) and the runner's sameness checks.
  Evidence: docs/decision_log.md D-033/D-044; joulewise/controller.py:1294
  (`_suite_rep_index_from_run_id`); scripts/run_campaign.py:438.
- Option B keeps ONE manifest/config hash per condition; the policy NAME
  changes the effective manifest (hence identity) once per campaign design,
  while per-repetition variation flows through controller-derived
  `order_seed`/`order_row` — exactly the D-045.6 seam built for this.
- P2-025 fail-closed prompt-hash checks key realized records by manifest
  `item_index` and item_id, not execution position
  (scripts/run_campaign.py:739-786), so Option B preserves them untouched as
  long as `item_index` keeps meaning MANIFEST index.
- Auditability: a skeptic holding only the bundle re-derives the expected
  permutation from (suite_manifest.json, order_policy, order_row) and checks
  it against realized `item_start` order — stronger than trusting Option A's
  baked order, equal in transparency.
- Option A's strongest case: zero runtime change, realized order == manifest
  order, existing validators keep working. It loses on identity fracture and
  on multiplying generator regeneration/config-matrix burden by B.

Consequence: implementation lands policy constants + pure permutation helper
in joulewise/suite.py, controller passes `order_row`, adapters execute the
realized plan, bundle_read validates realized order fail-closed.
Confidence: high.

### P30-2 [design] Rotation pins ratified by the lead

Decision (pins for the implementation):
1. Rotation unit is the contiguous BLOCK run; blocks whose items ALL carry the
   `sentinel` tag are position-anchored (suite-start/suite-end sentinels never
   rotate, D-046/C-015); all other blocks are the rotation vector in manifest
   first-appearance order. Level/block contiguity is preserved by
   construction (validator constraint stays intact).
2. Policies v1: `manifest_order` (identity, default, back-compatible),
   `block_round_robin_v1` (cyclic shift of rotatable blocks by row),
   `block_latin_square_v1` (Williams row-balanced Latin square; even N gives
   first-order carryover balance in N rows, odd N uses the standard 2N-row
   Williams pair). Within-block item rotation is DEFERRED (named revisit
   trigger), not silently included.
3. `order_row` = the controller's suite rep index (0 for single runs, the
   one-based `__rN` for experiment members); the permutation row is
   `order_row mod n_rows`. `order_row` is controller-derived, never
   runtime-chosen (extends D-045.6), recorded in `suite_start` metadata and
   `metadata.suite`. `order_seed` derivation and recording are UNCHANGED.
4. `item_index` stays the stable MANIFEST index everywhere; `position` is the
   realized execution ordinal; `prev_item` must be execution-honest.
   `outputs/suite_items.jsonl` stays keyed by `item_index` (P2-025 checks
   unchanged in semantics).
5. Back-compat: bundles with `order_policy == "manifest_order"` and no
   `order_row` stay strict-valid (existing corpus bundles unaffected); a
   non-manifest_order policy REQUIRES `order_row` and an exact match between
   the recomputed expected permutation and realized `item_start` order —
   fail-closed.
6. Pinned generated manifests (affine_smoke_v1, jw_mixed_v1, jw_sentinel_v1,
   mock) keep `manifest_order` and stay byte-identical this session; rotation
   is opt-in at generation time for future campaign manifests (a deliberate
   identity change per D-044).
Why: each pin resolves an open question from the design memo (sentinel
anchoring, rotation unit, row derivation, odd-N construction) in the direction
that keeps hash-domain closure and existing strict bundles intact.
Consequence: no joulewise/schemas.py change is needed (`metadata.suite`
validation is a required-subset in bundle_read.py; additive keys legal).
Confidence: high.

### P30-3 [PROMOTE-TO-DECISION-LOG] D-045.6 amendment: `order_row` companion to `order_seed`

Decision: `run_suite` gains keyword-only `order_row` (controller-derived from
the D-010 `__rN` suffix, 0 for single runs) alongside `order_seed`; realized
suite order is the pure function `realized_order(manifest, order_policy,
order_row)`; `order_seed` remains recorded identity/audit material and still
never implies reordering by itself. docs/decision_log.md is fenced this
session, so this rides the ledger for promotion: it amends D-045 pins 1 and 6
and should be recorded as D-045 amendment (or a new D-05x) at session
bookkeeping.
Why: a hash-truncated `order_seed` cannot COORDINATE distinct Latin-square
rows across B repetitions; balance requires the rep index. Recording
`order_row` makes the balance property verifiable from bundles alone.
Consequence: adapter_contracts.md gets a dated amendment;
prompt_sequencing_spec.md gets dated 2026-07-09 P2-030 sections including the
claims-wording downgrade path (reports say `manifest_order` when rotation is
absent).
Confidence: high.

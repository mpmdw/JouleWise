## Implementation and cache contract

- Kit builds resolve ten distinct historical `commit:path` inputs in one
  `git cat-file --batch` process. An invocation-local `ContextVar` shares the
  exact bytes across repeated references and resets even on failure. Each
  forced rebuild resolves Git anew; no process-global memo of abbreviated
  commits or cross-checkout files is kept. A `--check` snapshot spans its
  subsequent fresh readiness gate too, so that gate's repeated historical
  turn-cap reads reuse the same invocation's bytes without caching judgments.
- Normal generation uses `build/align-v4-cache/generation/`, already excluded
  by `/build/` in `.gitignore`. Its SHA-256 key covers `inputs.json`,
  `r1_slots.json`, the exact optional W1-plan bytes or explicit absence, all
  ten historical source byte digests, Python's version, and the content of
  every Python source under `joulewise/` and `scripts/`. The conservative code
  census also invalidates on a new lazy dependency. No mtime participates.
  Source hashing overlaps the historical Git batch using one background
  worker. Unreadable code refuses instead of silently omitting dependencies;
  symlinks and prohibited directory names are not followed.
- Hits return successful generated bytes and compare current destination
  bytes before writing. They repair changed/missing outputs and preserve
  unchanged files. Cold publication rechecks input digests. Cache entries
  carry payload checksums and publish by atomic replacement. Corrupt or
  unwritable cache storage falls back to a rebuild.
- `--check` always bypasses the generation cache, independently regenerates
  and compares every output byte, then calls the existing readiness gate.
  `--no-cache` also forces a normal uncached build. Pending/refused checks
  are never persisted or returned from cache.
- Receipt validation checks structure, signature, rulings, both gate
  verdicts, safe paths and SHA-256 of **all 221 artifacts plus two gate
  reports** on every invocation. A working-file refusal happens before Git
  I/O. A positive cache key additionally covers the complete receipt,
  freshly resolved committed blob IDs, validator/kit implementation digests
  and Python's version. A hit skips only repeated committed SHA-256
  comparisons; Git object existence is checked anew. `cache=False` forces
  all committed-byte comparisons. U3/WP19/readiness are not cached.
- Git replacement refs require special handling: Git can report an original
  blob ID while returning replacement bytes. A same-size synthetic replacement
  reproduced a stale-positive bug in the initial implementation. Validation
  now checks the replacement namespace (including `GIT_REPLACE_REF_BASE`)
  and bypasses the receipt cache entirely if any replacement exists.

The cache is disposable local acceleration, not registration evidence or an
approval credential. It relies on Git's normal content-addressed object
integrity. Current file reads are always fresh. As with the original code,
the checkout must remain stable during an invocation; this is not a filesystem
transaction against concurrent edits. Checking current files first changes
which refusal appears first when a request has several independent faults.

## Synthetic timings

Final measurements and raw samples are recorded in the companion
[timing JSON](2026-11-08-eng-kitcache-timings.json). Timings use Python 3.13.18 and the
baseline functions loaded from Git in the same interpreter. Each ordinary
row is the median of five runs; the complete 221-mutation loop runs once per
implementation. Temporary Git repos contain synthetic receipt text; the filled
W1/R1 fixture contains synthetic timing/configuration fields. Historical
config objects are repository code. No cited model or study-data path is opened.

| Component | Legacy seconds | Current seconds | Change |
|---|---:|---:|---|
| Skeleton generation, warm cache | 0.967 | 0.077 | 12.6× faster |
| Skeleton generation, batched `--no-cache` | 0.967 | 0.048 | 20.3× faster |
| Filled synthetic W1 generation, warm cache | 1.016 | 0.092 | 11.1× faster |
| Filled synthetic W1 generation, batched uncached | 1.016 | 0.043 | 23.4× faster |
| Pending `--check`, full regeneration then same refusal | 1.043 | 0.058 | 18.1× faster |
| Tiny synthetic receipt, warm cache | 0.117 | 0.135 | 16% slower |
| Tiny synthetic receipt, forced uncached | 0.117 | 0.109 | 1.1× faster |
| Filled synthetic static arm components | 1.316 | 0.196 | 6.7× faster |
| All 221 synthetic working-file mutations | 23.678 | 2.376 | 10.0× faster |

The arm row composes a filled synthetic kit's full regeneration/byte comparison
with synthetic receipt binding. It replaces the remaining readiness function
with that receipt validator solely for timing. It is **not a real arm**, does
not install anything, and excludes host probes, disk, battery, U3/WP19 and live
admission gates. The 221-mutation loop mirrors the expensive portion of the
existing receipt regression test.

Complete content hashing has a real cost: on these tiny inputs, the generation
cache can be slower than the new batched uncached builder. The latter remains
available through `--no-cache`; `--check` always takes that rebuild path.
The tiny receipt warm-cache row regressed by 18 ms: the fresh replacement-ref
and object-availability checks outweigh the avoided tiny blob transfer.
There is no demonstrated standalone receipt-hit speedup on this fixture.
Most savings come from batching, deduplication and refusing working drift before
Git reads. No minutes-to-hours
production saving is established by these sub-second synthetic components.
The host was not quiet and had the user's existing long job running; it was
not inspected or altered. Timing variation must not be treated as hardware
measurement evidence.

Reproduce without network, models, capture or registration:

```sh
python3.13 -B scripts/benchmark_align_v4_kitcache.py \
  --baseline-ref origin/align/2026-11-08-v4-r11 --rounds 5
```

## Equality and verification

The benchmark compares complete returned file dictionaries and written bytes
against the baseline generator for the pending skeleton and a filled synthetic
W1 plan, including derived sizing. Both implementations use the current
generator-file SHA so the comparison isolates behavior from the necessary
provenance refresh. A separate test uses independent legacy `git show` reads
and compares the complete generated dictionary to the batch/cache paths.
Pending `--check` refusal messages also match the baseline. Successful receipt
validation returns the original receipt object unchanged.

Committed generated changes are exactly the generator SHA in `plan_tree.json`
and its dependent tree SHA in `registration/identity_pins.json`. The scientific
configs, collection plan, receipt template and registration inputs are unchanged.

Failing-first evidence: the original nine cache regressions produced three
failures and four errors before implementation. The later Git replacement
regression and the readiness-snapshot sharing regression also failed before
their fixes. Final targeted verification is listed in the run report.
The test-only source-census fixture was adjusted to include
both code directories after unreadable-directory handling became fail-closed.

No full suite, Block-5 pipeline, real data, weights, network, hardware probe or
MLX execution was used. No MLX implementation changed, so this slice adds no
native MLX test requirement. Real W1 readiness and the exact-candidate receipt
for the landed code remain the lead's existing outside-sandbox gates. The
committed skeleton still refuses `--check` while prerequisites are pending.

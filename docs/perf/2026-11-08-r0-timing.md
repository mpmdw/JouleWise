## Reader and reproducibility

`--r0-result PATH` supports `joulewise.align.r0.report.v1`: explicit UTC run
bounds, monotonic `total_seconds`, sequential top-level `check_seconds`,
model/check identities, nested ladder turn and long-decode attempt `seconds`,
and census observation boundary pairs. `--r0-note PATH` accepts the specific
archival NOTE grammar used by re-run 11, extracting its timing columns and
explicit dwell milestones. The two options are mutually exclusive.

Neither input copies report payloads, correctness/selection values, sensor
values, model text, energies, residuals or scores into the worksheet. The
JSON reader parses the named blob in memory and projects only the allowlisted
timing/identity fields; it does not import any R0 capture/backend code.
Embedded paths are inert text. All source reads use the existing pinned
Git regular-blob reader: no working-tree record reads, symlink following,
discovery of live directories, fetch, network, LFS download or model loading.

chronologically unplaced R0 work. This is a different missingness question
from the **32.3 s** unassigned duration budget. There are no recorded check
boundaries to place the known 7,404.5 s on the epoch axis. Fabricating those
boundaries by stacking durations from the run start would hide admission and
inter-check gaps. R0-only input does not establish a window ceiling.

The 13 check durations and total have one decimal place. If each was rounded
to nearest, their subtraction has at most **±0.7 s** rounding error. The
0.2 s difference between the two run envelopes is compatible with their
different precision. Nanosecond arithmetic does not increase source precision.

idle/load/recovery, totalling 1,800 s. The observed check is 96.3 s longer;
that difference does not identify overhead, extended idle, or postprocessing.
No actual subphase boundaries are committed here, so those configured values
are not inserted into the ledger as observations.

## Top sinks and speedup candidates

| Sink | Minutes | Share of R0 wall |
|---|---:|---:|
| Long decode | 55.28 | 44.60% |

Model load plus load qualification is only **102.7 s (1.38%)**. Removing the
entire 32.3 s remainder would save **0.43%**. The opportunity is concentrated
inside the four large checks; the available record does not decompose their
GPU, waiting, serialization, and host work.

**No speedup has been implemented or measured in this task.** Expected
savings cannot be point-estimated for unidentified subcosts. The engineering
figures below are explicitly conditional planning scenarios or upper bounds,
not empirically supported forecasts. Changes to workloads, qualification
coverage, ordering, freshness or quiet rules belong in B even when easy to code.

### A — pure engineering, preserve R0's test design

| Candidate | Concrete implementation and evidence | Expected saving / uncertainty |
|---|---|---|
| Cache/stream report rendering | `r0_runner.save_report` serializes the entire accumulated JSON and Markdown on progress callbacks; `r0_mlx._fixed_context.observe` issues frequent callbacks. Cache unchanged serialized sections while preserving every existing durable snapshot and identical final bytes. The NOTE confirms large reports; no serialization time is recorded. | **Unknown.** A 1–5% reduction in the combined long-decode/ladder/memory checks would save **53–266 s**; this is a benchmark target, not a prediction. Full check wall (5,326.3 s) is only a loose ceiling, not removable serialization cost. Validate with invented records and byte-equality checks first. |
| Faster inventory hashing with identical coverage | Improve buffer/read/hash implementation within `disk`; still read and hash every byte and retain all identity checks. Low priority for an hours goal. |
| Automate a separate timing-only committed export | Use this reader's projection, source digests and existing recorded fields; keep original full reports immutable and preserve their custody. Primarily removes the evidence gap blocking the next optimization decision. |

No candidate may change chunking, sampler, cache policy, model, pins, decode

### B — changes R0's design; requires lead/protocol decision

| Candidate | Design change / evidence at risk | Expected saving under stated assumption |
|---|---|---|
| Reuse a qualified SMC selection when identity/freshness permits | Stop redoing selection on every otherwise identical R0. Current policy performs a fresh step; define invalidation, sensor/stack identity and freshness before reuse. Keep PROVISIONAL labels. | **≈1,896.3 s (31.61 min) per avoided step**, minus new verification cost. This is the observed whole-check cost, not a claim that 900 s load or 600 s recovery may be shortened under current rules. |
| Combine full-context peak/swap and long-decode evidence | Cover memory qualification during one approved combined stress test. Obtain a timing-only rung export before choosing this. |

Avoiding SMC plus replacing the standalone memory check has an arithmetic
potential of **2,640.7 s (44 min 0.7 s)**, leaving about **79 min 56.1 s**
inside R0 before new verification costs. That is not an approved combined
design or a forecast: ordering and changed heat history can invalidate simple
addition. Long decode alone still accounts for almost an hour.

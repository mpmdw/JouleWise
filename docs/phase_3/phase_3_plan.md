## Goal And Research Questions

Decompose disaggregated (split prefill/decode) inference into measured
prefill energy, transfer energy, and decode energy, across heterogeneous
device pairs and interconnect speeds, to answer:

- Q1: Under what conditions (model size, prompt length, link speed, device
  pair) does splitting inference reduce total energy versus running
  monolithically on either device?
- Q2: How sensitive is the split's energy cost to interconnect bandwidth -
  where is the crossover, and does 2.5GbE materially move it versus 1GbE?
- Q3: What does the energy-latency trade-off look like - when splitting
  saves energy, what latency does it cost (and vice versa)?

Every Q maps to figures in the Phase 4 registry (F4, F5, F6, F7).

## Feasibility-First Strategy

This phase is built around D-015's ladder because KV-cache portability is
the project's central feasibility risk (R-004, R-005). Restated:

1. Stage 3.1 *synthetic transfer microbenchmark* - guaranteed deliverable,
   no runtime cooperation needed. Even in the worst case, this plus Phase 2
   baselines supports an analytical split-energy model.
2. Stage 3.2 *offline replay* - primary real mechanism: persist prompt
   cache on node A, move the file, resume decode on node B, same pinned
   runtime on both ends.
3. Stage 3.3 *live split* - stretch only; never a dependency of the phase's
   acceptance.

Hard rules (D-015): same runtime and pinned version on both ends of any
real KV transfer; cross-runtime KV portability is out of scope; no borrow
window or lab session is scheduled until Stage 3.0 verdicts exist.

The honest-degradation principle: each rung that fails converts the rung
above into a documented applicability finding plus an analytical
composition, both reportable. Nothing in this phase fails silently into
"no result".

## KV-Cache Size Model

Transfer payloads are KV caches; their size is analytically predictable and
drives every experiment-design choice (prompt lengths, payload sweep range,
expected transfer times). Derivation, for standard multi-/grouped-query
attention with fp16 cache:

```text
bytes_per_token = 2 (K and V) × n_layers × n_kv_heads × head_dim × 2 (bytes, fp16)
```

Reference table (verify n_layers/n_kv_heads/head_dim against each chosen
model's config.json when D-016 closes; correct this table if they differ):

| Model | layers | kv_heads | head_dim | KiB/token | MiB @2048 tok | MiB @8192 tok |
|---|---|---|---|---|---|---|
| Qwen2.5-1.5B | 28 | 2 | 128 | 28 | 56 | 224 |
| Llama-3.2-1B | 16 | 8 | 64 | 32 | 64 | 256 |
| Qwen2.5-7B | 28 | 4 | 128 | 56 | 112 | 448 |
| Llama-3.2-3B | 28 | 8 | 128 | 112 | 224 | 896 |
| Llama-3.1-8B | 32 | 8 | 128 | 128 | 256 | 1024 |

Expected transfer times at practical TCP throughput (~112 MiB/s on 1GbE,
~280 MiB/s on 2.5GbE, ~1120 MiB/s on 10GbE), for a 2048-token prompt:

| Model | 1GbE | 2.5GbE | 10GbE |
|---|---|---|---|
| Qwen2.5-1.5B (56 MiB) | ~0.5 s | ~0.2 s | ~0.05 s |
| Qwen2.5-7B (112 MiB) | ~1.0 s | ~0.4 s | ~0.1 s |
| Llama-3.1-8B (256 MiB) | ~2.3 s | ~0.9 s | ~0.23 s |

Reading: at 1GbE, transfer time for mid-size models is the same order as
prefill time on weaker devices - exactly the regime where a crossover can
exist. This is why the sweep must span payloads from ~16 MiB to ~2 GiB
(log-spaced) and why prompt length is a primary experimental axis.

Caveats (recorded so the table is not over-trusted): real serialized caches
differ from the formula via dtype (llama.cpp can store q8_0 cache: ~half),
metadata overhead, and runtime-specific layout. Stage 3.0 spikes record
*actual file size vs predicted* per runtime; the deltas calibrate this
model. A `joulewise kv-size` helper (Stage 3.0.0) computes the formula per
model config so sweep configs are generated, not hand-calculated.

## Stages

### Stage 3.0: KV Persistence Feasibility Spikes

All spikes are hardware-light (Mac + any one CUDA box), run before any
scheduling of borrowed hardware, and write verdicts to
`docs/phase_3/kv_feasibility.md` using codes: `replay_supported`,
`replay_unsupported`, `partial(<limitation>)`.

#### Stage 3.0.0: KV-size helper

Objective: `python3 -m joulewise kv-size <model-config.json|params>` printing
bytes/token and totals for given prompt lengths.
Actions: implement from the formula; unit tests against the table above.
Evidence: tests + table regenerated by the tool.
Acceptance: tool output matches hand calculation for two models.
Fallback: none needed.

#### Stage 3.0.1: mlx-lm prompt-cache spike

Objective: prove/refute persist-and-resume on Mac.
Inputs: Mac with `[mac]` extra (Slice 2G complete), chosen small model.
Actions: prefill a 1024-token prompt; save the prompt cache via mlx-lm's
cache API (expected surface: `make_prompt_cache`/`save_prompt_cache`/
`load_prompt_cache` or the `mlx_lm.cache_prompt` CLI - verify against the
installed version, do not trust this plan's memory of the API); record
actual file size vs predicted; load in a *fresh process*; decode 64 tokens
greedily; diff against an unsplit greedy run of the same prompt.
Evidence: commands, file sizes, token-level diff result, in
`kv_feasibility.md`.
Acceptance: verdict assigned; greedy outputs identical (or divergence
explained and bounded).
Fallback: verdict `replay_unsupported` => Mac participates via llama.cpp
(3.0.2 covers it); record runtime substitution.

#### Stage 3.0.2: llama.cpp prompt-cache spike (including cross-machine)

Objective: same as 3.0.1 for llama.cpp, *plus* the portability question that
gates all heterogeneous pairings (R-005): does a cache saved by a CUDA
build restore correctly in a Metal build?
Inputs: same pinned llama.cpp release built on both machines; identical
GGUF file (hash-verified) both ends.
Actions: same-machine save/restore first (`--prompt-cache` /
`--prompt-cache-all`, or the server slot-save API - record which); then
CUDA-save -> scp -> Metal-restore; greedy-diff in both cases; record file
size vs prediction (note q8_0-cache option effect if used).
Evidence: as 3.0.1, plus an explicit `cross_machine_portable: yes|no|partial`
finding.
Acceptance: verdicts for same-machine and cross-machine recorded separately.
Fallback: cross-machine `no` => heterogeneous pairs use analytical
composition (R-005 fallback); same-platform pairs proceed.

#### Stage 3.0.3: vLLM KV-export spike (time-boxed)

Objective: confirm or refute file-based KV replay on vLLM within one
session; expected verdict is `replay_unsupported` for file replay (vLLM's
disaggregation support is connector/streaming-shaped and version-volatile).
Actions: survey the installed version's KV-transfer/connector APIs;
attempt the smallest possible persist-or-transfer demonstration; time-box
to one session - the point is a verdict, not a port.
Evidence: version, APIs found, attempt log, verdict.
Acceptance: verdict assigned either way; if `replay_unsupported`, GPU nodes
use llama.cpp-CUDA for split experiments (vLLM remains the monolithic-
baseline runtime where chosen).
Fallback: built into the objective; no further fallback needed.

#### Stage 3.0.4: Verdict consolidation

Actions: fill the pairing-feasibility matrix in `kv_feasibility.md` (which
device pairs are reachable with which runtime, given verdicts); re-rank the
Stage 3.4 experiment matrix accordingly; update the risk register entries
R-004/R-005; log any decision changes.
Acceptance: Phase 3.2+ scope is justified entirely by recorded verdicts.

### Stage 3.1: Schema v0.2 + Transfer Microbenchmark

#### Schema v0.2 (D-008)

Objective: implement the already-designed config extension before any split
data exists.
Actions: add `run_kind` (default `monolithic`), `split_plan`
(prefill_target, decode_target, transfer{method, staging_dir, link_label}),
`transfer_bench` block; per-run_kind validation rules; `deserialize` phase
label; v0.1 configs must validate unchanged (regression test); bump
schema_version handling; update `print-config-schema`.
Evidence: schema tests including v0.1 backward-compat; updated examples
(`configs/examples/transfer_bench.json`, `split_offline_example.json`).
Acceptance: validation rules per run_kind are enumerated in tests; no
consumer breaks on v0.1 input.
Fallback: none needed (designed change).

#### Transfer microbenchmark

Objective: measured transfer time and *both-end* transfer energy versus
payload size and link, independent of any LLM runtime.
Design notes:

- `python3 -m joulewise transfer-bench` config-driven (run_kind
  `transfer_bench`): receiver role started on the remote node via the 2K
  remote-runner protocol; sender streams N bytes over TCP; both nodes
  sample power for the transfer window (telemetry adapters per node);
  payload manifest (bytes, sha256, timings) recorded.
- Clock alignment per D-003: marker events before/after; offset bound in
  metadata; reducer flags intervals below the bound.
- Energy attribution per methodology: sender energy and receiver energy
  reported separately *and* summed; idle-subtracted both ends.
- Loopback mode (localhost) for CI smoke - no energy meaning, exercises
  the machinery.
- Payload ladder: 16, 64, 256, 1024, 2048 MiB (log-spaced, KV-table
  motivated), n>=3 per point per link.

Actions: implement bench + composite-bundle writing (see 3.2 layout);
loopback test in CI; first real two-node run on whatever pair P1-004/P1-006
evidence permits.
Evidence: loopback CI test; real-pair bundles with energy/GiB numbers in a
run report; link verification commands recorded per the network plan.
Acceptance: energy/GiB and effective throughput with uncertainty for at
least one real link; methodology's clock-offset bound respected.
Fallback: if no second node is available yet, the loopback path plus the
bench being demo-ready is the deliverable, and the stage closes pending
hardware with the blocker recorded (the bench is then run early in 3.4).

### Stage 3.2: Offline Split Runs (Replay)

Objective: real split measurements: prefill on node A (measured), cache file
transferred (measured by the 3.1 machinery), decode-from-cache on node B
(measured).

Design notes:

- Orchestration: controller drives the stages sequentially via transports;
  stage boundaries emit `serialize`/`transfer`/`deserialize` phase events;
  the transfer leg reuses the 3.1 path (same code, real payload).
- Composite bundle layout (extends `run_bundle_layout.md`):

```text
runs/<run_id>/
  config.json                  (split config, v0.2)
  metadata.json                (composite; per-node clock bounds)
  events.jsonl                 (controller + merged node events, node field)
  summary_metrics.json         (composite: per-stage energy decomposition)
  transfer/payload_manifest.json
  nodes/prefill/               (standard bundle artifacts for node A)
  nodes/decode/                (standard bundle artifacts for node B)
```

- Stage accounting definitions (pinned here so reducers and prose agree):
  serialize = cache-persist call window on A; transfer = byte-movement
  window; deserialize = cache-load window on B; decode = first-token to
  last-token on B. Cache load is *not* part of decode energy.
- Warm-state policy: node B has the model loaded and warmed before the
  measured window (model load is a fixed cost shared with monolithic
  serving, not a per-request split cost); recorded explicitly in
  metadata so the accounting choice is auditable. The alternative
  accounting (cold decode node) is a possible sensitivity run, not the
  default.
- Equivalence check per run: greedy decode output compared against a
  monolithic greedy run with the same prompt (correctness guard inherited
  from the spikes).

Actions: implement split orchestration for the pairings green-lit by 3.0.4;
run smoke splits on the cheapest available pair; then measured splits
(n>=3) for each feasible pairing at one link speed.
Evidence: composite bundles validating; per-stage energy decomposition
summing (within tolerance) to measured totals; run reports per pairing.
Acceptance: at least one pairing produces complete split decomposition
(prefill_E, transfer_E, deserialize_E, decode_E) with uncertainty; every
planned-but-infeasible pairing has a recorded reason.
Fallback: R-004/R-005 ladders - analytical composition using 3.1 transfer
energy + Phase 2 phase-attributed baselines; reported as modeled, never as
measured.

### Stage 3.3: Live Split (Stretch)

Objective: stream KV during the run (socket, no intermediate file) for one
same-platform pairing, if and only if 3.2 is complete and healthy and the
calendar (P1-008) permits.
Design sketch: llama.cpp server slot save/restore over the wire, or direct
socket streaming of the cache buffer; same composite bundle; `split_live`
run_kind.
Acceptance: one live split run decomposed as in 3.2; comparison live vs
offline overhead reported.
Fallback: explicitly droppable (R-012 ladder rung 1); its absence does not
block phase exit.

### Stage 3.4: Interconnect Sweep + Crossover Dataset

Objective: the headline dataset for Q1/Q2/Q3.

Experiment matrix (pruned by 3.0.4 verdicts and hardware reality; full
grid is the ambition, recorded subset is the plan):

- Pairings: 3050<->Mac, 3050<->Orin, Orin<->Orin, Orin<->Mac, and
  GPU<->GPU during the 3080 Ti borrow window (R-006 runbook: tooling
  rehearsed beforehand; borrow time is execution-only).
- Links: 1GbE, 2.5GbE, optional 10GbE (per network plan evidence; direct
  cabling preferred per R-011).
- Models: D-016 small + mid.
- Prompt lengths: 512, 2048, 8192 (KV table column anchors), decode 256.
- Reps: n>=3 (n>=5 for the headline pairing), D-014 protocol.
- Monolithic references: from Phase 2M baselines, re-run only if model or
  software versions changed (config hash decides).

Crossover analysis inputs defined now (Phase 4 computes): for each pairing
and link, total split energy vs prompt length against both monolithic
references; crossover = prompt length where split total drops below the
better monolithic option; report when no crossover exists in range (a
legitimate answer to Q1).

Actions: generate matrix configs by script; execute in scheduled hardware
sessions per the borrow runbook; validate bundles continuously
(`validate-bundle` after each session, not at the end).
Evidence: experiment manifests covering the executed subset; session run
reports; the dataset passes Phase 4's aggregation without exclusions beyond
documented ones.
Acceptance: crossover dataset spans >=2 link speeds × >=2 prompt lengths ×
>=1 pairing with n>=3; every planned cell is either filled or has a
recorded reason.
Fallback: R-006/R-011/R-012 ladders; minimum publishable floor = synthetic
sweep (3.1) + one real pairing (3.2) + analytical composition for the rest.

## 2. Minimal sequence after pruning, and can it be a script
Pruned rules (docs/process_prune_2026-09-29.md): no per-window arm gate or lens (cold gates only for registrations, claim results, irreversible acts), #416 once per code change, emails only on change of state, routine window = raw-byte validation + independent arithmetic (what harvest_window does). Rev 6 replaces the 6 h spacing with physics (§6.2); the driver itself checks census, thermal, idle power, OFF receipt, 600 s clean dwell at t0. So window k+1 needs only the next-window decision from window k.
Minimal loop (block runner, one state file in `night-custody/block-<id>/`):
 a. WAIT terminal: `night/result.json`, `chain.exited`, `courier.sent` (or courier attempts exhausted), process census clear. Stop/NO channels polled throughout.
 b. PRE-HARVEST: rebuild coordinates (`harvest_window.coordinates`), `terminal-pin` + `advance-head-pin` (dry run, execute), `battery-verdict`, one commit (branch `harvest/<session>`).
 c. HARVEST: `harvest_window.py --plan --custody ~/night-archive/harvest-<plan> --preregistration ... --prior-harvest-record ... --session-ids ... ` (preserves, authenticates, counts, uninstalls). rc 0 and `next_window.verdict == NEXT_WINDOW`, else HALT and notify Ed (STOP_TO_REVIEW, CLOSE_AND_DERIVE, null session, any refusal).
 d. LAND pin/verdict on main (PR + CI + `--merge`). See gap G1.
 e. ARM k+1: t0 = now + lead; steps 0-6 with the Rev 6 variants: v4 plan via `gen_derivation_night.py --plan-template T --quiet-admission-json P --new-plan OUT --new-plan-id ID --prior-revision6-session S --prior-harvest-json HJ --prior-started-epoch-s A --prior-terminal-epoch-s B` (harvest JSON's `next_window` must authenticate to NEXT_WINDOW; manifest written to custody), emit + `--verify` wrapper, preflight, render, notice, publish, probe, install, verify.
 f. Sleep to k+1's terminal (runner idle, no CPU, no agent-named argv).
Yes, it can be a deterministic script using existing commands, with the gaps below. Per-window wall, best case: 134 min chain + 20 harvest + 10-15 arm + 10 install lead ~ 3 h start-to-start, +30-45 min if landing waits on hosted CI; `plan_span_active` blocks arm discovery until t0+155 min (about 21 min dead time) unless `window_max_s` is trimmed (changes plan digests; Ed's call).

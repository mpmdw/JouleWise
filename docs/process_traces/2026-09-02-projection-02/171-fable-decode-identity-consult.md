## Q1 — what the identity is under the contract's own rules

- `scientific_config_identity` = the whole typed config minus `run_id` and minus block/replacement/`repN` tags (`ip:217-236`); it keeps `workload_profile` verbatim, so `suite_manifest_ref`/`sha256` (written per prompt at `gen:1884-1896`) and the `decode-prompt=` tag (`gen:1857-1863`) each split the identity. The unit pin hashes exactly this (`ip:349-372`, `:1459`).
- The declared decode identity (`gen:2550-2610` from `workload_for`, `gen:1323-1350`) carries `prompt_tokens: 42` and no manifests; the schema forbids that combination on the real config (`joulewise/schemas.py:62-69, 291-317`), so the declaration describes a config that can never exist, not a drift.
- The referenced floor plan `../d117_floor_<model>_v5/calibration_plan.json` (`gen:2550-2610`) exists NEITHER in the generated root nor in the repo (`ls configs/campaigns | grep d117_floor` → v3 only); `_validate_unit_bindings` is shape-only and never resolves it (`ip:140-141, 419-446`). So "the floor's decode identity" is currently undefined; R-3 only says the cell calibrates one workload (`docs/process_traces/2026-08-28-workload-consult/04-MAGISTRATE-RULING.md:39-50`).
- Floor↔consumer binding never uses `config_set_sha256` equality: `floor_request_for_evidence` keys on backend/metric/window_class/stack identity plus either the condition-family allowlist or exact-cell scientific identity (`inputs:3849-3960`), and it requires ONE consumer scientific identity across the evidence (`inputs:3873-3881`). v3 proves this: consumer `A/decode` config_set `604f6e22…` vs floor unit `alpha` `bf0ea6a3…`, sharing only model_artifact/runtime pins (`configs/campaigns/d117_contrast_qwen25_1p5b_vs_7b_v3/identity_pin_projection.receipts/projection-0001.json`; `configs/campaigns/d117_floor_qwen25_1p5b_v3/identity_pin_projection.receipts/projection-0001.json`). D-131 cl.2's "same triple" therefore means model/runtime pins plus a per-unit config pin (`DL:8394-8442`).
- The mint has the same one-identity rule (`scripts/mint_floor_artifact.py:755-787`; generalized `scripts/mint_floor_artifact_generalized.py:2317-2344`), and the condition family is keyed by `prompt_tokens` (v1) or a SINGLE `suite_manifest_sha256` (v2) (`joulewise/floor_extraction.py:690-716`) — neither shape names an eight-set today.
- Code precedent that "which prompt" is collection-varying: `realized_scientific_identity` deliberately excludes the prompt hash (`inputs:2503-2513`); block-assignment tags are already stripped (`ip:158-163, 231`); D-166 rotates one prompt per block by `decode_prompt_index` (`gen:1394-1396`, block rule `d166_block_prompt_cycle.v1` `gen:1698-1710`) and R-1 forbids same-8-per-member (`04-MAGISTRATE-RULING.md:25-31`).
- Answer: yes, the arm has ONE identity — profile + closed manifest set — but only once the config says so. Profile-only identity is wrong: the exact-cell floor route (`inputs:~3905`) would then bind a floor minted on a different prompt set.

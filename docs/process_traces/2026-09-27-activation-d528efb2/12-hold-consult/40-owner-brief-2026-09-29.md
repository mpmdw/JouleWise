# D-138 owner brief, 2026-09-29 (Fable 5.1, interactive session bc060503)

Ed asked for more information before choosing among the ruling's options (a), (b), (c). This brief is written to be read without project shorthand. The magistrate does not choose; it recommends, with the reasoning shown.

## 1. What the decision is about

**The file.** `configs/calibration/calibration_acceptance_d079_v2_n12_25g83_r1.json` is the *calibration file* for the new operating-system build 25G83: it states how large the instrument's timing uncertainty may be before a measurement is refused. It was derived from the 12 valid captures of the two derivation windows W1 and W2 on 09-27. Ed approved its name and its release "after every gate passes".

**The hold (H1).** The science ruling for this file says: no *claim-bearing* window (one whose results may be reported as findings) may run at build 25G83 until the estimator-cap question is closed by a written ruling. Windows that carry no claim may run; they are how the cap evidence is gathered.

**The transaction (D-138).** One reviewed pull request that (1) repairs the calibration loader, (2) adds a re-runnable promotion tool, (3) registers the new file in code, and (4) builds the hold into the code so that registering the file cannot let a claim-bearing measurement use it at 25G83.

## 2. Why it stopped

Part (4) was rebuilt three times. After each round a fresh reviewer, told to try to get around the hold, found a *route*: a sequence of calls into unmodified production code that ends with the held file's content or numbers coming back, or a claim-bearing campaign starting. The cold ruling HOLD-BY-CONSTRUCTION-01 set the stop rule in advance (§6.2): round 3 is the last; **any route found after it stops the transaction for good**, with no round 4, and the choice goes to the owner. Round 3's reviewer found three routes, so the stop applied. Reading those routes as "not real" would be reinterpreting a ruled stop condition, which the magistrate may not do.

## 3. The three routes, in plain words

1. **Calling the campaign function directly.** The command-line entry point checks the build and refuses (exit 2). But a Python caller that imports the campaign function and calls it directly skips that check and reaches the point where a claim-bearing child process would start. In the production code, the command-line entry point is the *only* caller. Someone would have to write new Python to take this route.
2. **A private byte-authenticating helper.** Handed the held file's bytes directly, the internal helper (an underscore-named function) returns the full parsed file. The public wrapper around it refuses the held file.
3. **A private number-lookup helper.** Handed the held file's identifier directly, a second internal helper returns its screen value, 0.013701 s. The public function around it refuses.

The same reviewer established that **no production caller carries any of these results through to a claim**: the public wrappers refuse, inspection output fails re-authentication when presented to claim consumers, and bracket evaluation (the step every reported number must pass) still refuses any passing bracket at 25G83. So today no claimable number can be produced at 25G83 by any existing code path. The routes count because the ruling's definition (§6.1(4)) deliberately counts held content returned by any function other than the inspection function, whether or not anything downstream uses it.

**Also found, separately (contract refuter 3):** four of main's test files fail on the candidate. All fail closed (they refuse more, not less) and none is a route. Every cure edits a test on main, and the ruling says whether that weakens anything needs a ruling, not the lead's judgment. The candidate's whole suite shows 6 failures and 9 errors in 5 modules.

## 4. A fact that shapes the choice

On main today, **no calibration file for 25G83 exists in code**. The only registered file judges the old build 25F84. A measurement at 25G83 therefore matches no build any registered file judges, and bracket evaluation returns "stale" and refuses it. In other words, H1 is already enforced on main by absence. **Registering the new file is what creates the risk that the hold exists to counter.** If the file is not registered, there is nothing to hold.

The file is also **interim**. The cap council (CAP-COUNCIL-25G83-01 and its addendum) chose route R: freeze the estimator code, size the cap from at least 24 non-claim captures under a pre-registered rule, then **re-issue the calibration** (two re-issues are planned). The r1 file would be superseded by that re-issue before any claim-bearing window runs at 25G83.

The non-claim windows that gather the cap evidence do not need r1 registered: they run by the derivation route, which requires the default file to *not* judge the machine's build (that is how W1 and W2 ran). Nor does the network-time lane (N1, which must land before any 25G83 window) depend on r1.

## 6. Recommendation

**(a).** The hold exists to counter a risk created by registering an interim file that will be superseded anyway; not registering it removes the risk with nothing to enforce. The critical path to a claim-bearing 25G83 window is the cap sizing (non-claim windows) and the network-time lane, and neither needs r1 in code. When the cap is sized and H1 lifts, the re-issued file lands through a plain registration with no hold to build.

**What (a) does not do:** it does not merge a code-level, build-keyed hold. If Ed wants that mechanism regardless (for example, as protection against a future interim file), it becomes a separate lane, designed once the cap plan's file sequence is fixed, rather than a fourth round now.

**One thing not confirmed:** whether any planned non-claim window or the H7 comparison needs the r1 file registered in code. The record's earlier brief said nothing scientific is lost, and no such need was found in the ruling's facts (F12, F13) or the cap plan, but it was not exhaustively searched.

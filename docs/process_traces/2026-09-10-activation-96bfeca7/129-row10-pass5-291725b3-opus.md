With `--session-ids`, `check` returns the dry-run code (0 here) while printing

**Is that acceptable? My view: yes, leave it — but the rc silence is pre-existing,
not introduced here.** At `bd22ed19` the mismatch went into `errors`, and `errors`
is *also* invisible to the `return dry_run_code` path (`git show
bd22ed19:scripts/…py` line 335: `return 3 if errors or mismatches else 0`, reached
only when `not named`). So this diff changes WHERE the verdict prints, never its rc
weight on the dry-run path. Three reasons to accept:

- The desk step in runbook 99 runs the watch with no session ids, and on that path
  the verdict now *does* drive rc (`preregistration_failed` joined the condition) —
  which is a strict improvement over `bd22ed19`, where it drove rc via `errors` but
  at the cost of the byte-identity property.
- The dry run answers a different question by design (the comment at :345-348), and
  a drifted epoch is the very reason a new corpus is being captured; masking the
  registration's own answer with an epoch verdict would defeat the subcommand.
- Issuance is independently fail-closed: `prepare-candidate` refuses on the
  pre-registration digest pin (:1174) and on the epoch pins (:1179), with a test
  asserting the refusal text `"is not the pre-registered b762e5bf"`. Nothing can be
  issued off a `check` rc of 0.

If the lead wants belt-and-braces, the minimal change is to make a
pre-registration failure force the dry-run path non-zero as well — but that would
newly conflate two exit codes (`3` epoch drift vs `DRY_RUN_INADMISSIBLE_EXIT = 5`
registration not ready) that :161-164 deliberately keeps distinct. I do not
recommend it.

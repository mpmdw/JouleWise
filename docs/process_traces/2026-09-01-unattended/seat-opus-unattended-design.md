## Q3 — scheduler and wake layers

**User LaunchAgent, `LimitLoadToSessionType Aqua`, `RunAtLoad false`,
`StartCalendarInterval`.** Grounds, bench-verified:

- Must run as `edr`: `sudo -n -l` on this machine returns
  `(root) NOPASSWD: /usr/sbin/systemsetup -setusingnetworktime off, … on` and
  `(root) NOPASSWD: /usr/bin/powermetrics`. A root LaunchDaemon would run the
  sampler as root without sudo — a different lineage than every reviewed capture.
- **powermetrics needs no GUI and no TTY.** Form is `sudo -n`
  (`joulewise/adapters/powermetrics.py:127`, `:1480-1497`); no `requiretty`
  appears in the machine's `Defaults` line for `edr`; the repo's only
  `!requiretty` is on the *network-time* alias
  (`scripts/joulewise-network-time.sudoers:3`); no `LimitLoadToSessionType`
  anywhere in the repo today.
- **But the night does need Aqua**: `pmset displaysleepnow`
  (`run_campaign.py:1019`, `quiet_mac_prep.sh:92`) and `osascript` System Events
  (`quiet_mac_prep.sh:17-27`). LaunchAgent, therefore — not Daemon.
- **No wake event is needed.** Bench `pmset -g custom`: AC `sleep 0`,
  `displaysleep 0`. Do **not** add `pmset schedule wake`. Note `powernap 1` and
  two live `com.apple.alarm` wakes in `pmset -g sched` as a registered
  contamination residual.

**Two independent wake layers (D-127 cl.4 "never one mechanism"):** (1) the
LaunchAgent's `StartCalendarInterval`; (2) a **crontab** entry for the same driver
at T-0+5 min — a different timer implementation with different failure modes.
Honest residual to record: both are ultimately parented by launchd, so this is
*implementation* independence, not root independence. Idempotence: the driver
takes an `O_EXCL` lock named by the night id; layer 2 no-ops if the lock exists
and layer 1's heartbeat is fresh.

**Missed-fire guard — the packet omits it and it is a wrong-number risk.** launchd
replays a missed `StartCalendarInterval` job at the next opportunity, which for a
window means measuring at 09:00 with Ed typing. The driver **must** refuse when
`now` is outside the pre-registered T-0 ± tolerance: reason `night_window_expired`.

**"Stand down on liveness proof", concretely (T2).** Supervisor writes
`$NIGHT_ROOT/relaunch/attempt-<n>.json` `{attempt, argv, spawn_monotonic_ns,
boot_session_id}`; the fresh session's **first scripted action** writes
`heartbeat-<n>.json` `{schema, attempt, session_pid, boot_session_id,
written_monotonic_ns}`; the supervisor stands down when that file exists with
`written_monotonic_ns > spawn_monotonic_ns` and matching boot session. Deadline
**300 s**; retries 3, backoff 60/180/600 s.

**I dissent from the brief's premise here.** The T26 600 s is a *clock-evidence*
liveness bound between R1 batch completion and validity origin, on the ordinary
monotonic clock, derived from 11 × `_PROBE_TIMEOUT_SECONDS = 45` + 105 s =
`_MIN_IDLE_NS` (`COLD-GATE-RULING.md:202,211,229`;
`arm_readiness_evidence_t0.py:51,54`). It has **nothing to do with a relaunch
heartbeat**. Borrowing it would repeat exactly the defect that ruling struck — a
constant travelling outside its derivation. The relaunch deadline needs its own
derivation: measure a cold `claude -p` start once on this machine and record it.

**A failed night** writes `$NIGHT_ROOT/night-refusal.json` (reason code, failing
condition, evidence hashes), attempts **no** measurement, and the courier emails
it. The retry budget covers only *relaunching the agent* — never
`run_campaign.py`. Keep that structural, not conventional: the measurement path
gets no retry loop in the source at all, mirroring `launch_window.py:262-263`.

## Q4 — who observes the machine when nobody is on it

Three records, only one of which is worth anything alone:

1. **Agent's last act (self-declared, weak):** `$NIGHT_ROOT/agent-exit.json` =
   `{schema, agent_pid, agent_argv, boot_session_id, exit_intent_monotonic_ns}`,
   then the session exits.
2. **Launcher's independent observation (the real proof):** the launchd-fired
   driver is **not a descendant of the agent**. It verifies `kill(agent_pid, 0)`
   fails *and* takes its own census with the **production** predicate —
   `/usr/bin/pgrep -lf "codex|claude|t3"` requiring exit code exactly 1 with empty
   stdout (`arm_readiness_evidence_t0.py:1312-1314`, `:1724`) — plus
   `pgrep -x caffeinate` (`:1723`). It records `pre_launch_census` as pid+argv rows.
3. **Capture-time censuses:** the same predicate at each `stage_start`/`stage_end`
   seam (`SHAKEDOWN-G2-RUNSHEET.md:366-379`), appended to `capture_censuses`. A
   census finding an agent **aborts the remaining stages** and writes a refusal.

**Use the strict spelling, once.** G8's `_AGENT_TOKEN_RE`
(`t0_rehearsal.py:57`) is boundary-anchored and the producer row's own acceptance
records it missing `codex-helper`, `claude-code`, `/usr/local/bin/codex-run`. One
predicate — the production one — in one module.

**Idle T3-Code window: refuses, and that is correct.** `_expect_absent` needs
exit 1 + empty stdout; an idle `claude` at a prompt matches `pgrep -lf`. It must
refuse **before the ledger reservation**, so a botched night costs an email and
nothing else. The email must quote the surviving argv so Ed knows what to close.
Bench right now: `pgrep -lf "codex|claude|t3"` returns **586** lines, and
`pgrep -lf caffeinate` shows three live `caffeinate -i …/codex-run-v3` wrappers —
an ordinary working day fails this by orders of magnitude, which is precisely why
the census must be the driver's *first* act.

**Should the headless session replace the interactive one on window nights?**
Yes, and stronger: from ~T-0−15 min through completion there must be **zero**
sessions, headless included. The headless session's role is *bracketing* — arm
before, harvest after — never presence during.

## Q5 — interaction with the running /loop

1. **Arming turn (T-0 − 60 min):** write `$NIGHT_ROOT/night-plan.json` (night id,
   scheduled T-0 ± tolerance, driver path + sha256, config-root digests,
   pre-registration digests, receipt path, courier time); install/refresh both
   wake layers; write `$NIGHT_ROOT/handback.md` — **the file the relaunched
   session reads first** (what was armed, what to check, the exact Sol/Opus briefs
   to issue, the kernel rows to advance).
2. **Stand-down turn:** refresh `RUN_STATE`'s header, write `handback.md`,
   `agent-exit.json`, **and end the session.** This is a real behavioural change:
   the standing turn-end rule (never end a turn with zero live background work)
   must be explicitly suspended on window nights, because live background work
   *is* the contamination. It needs a ruling (Q6.4).
3. **Courier turn** (completion + 5 min; dead-man at 07:00): launchd starts
   `claude -p` with a fixed prompt — "read `handback.md` and `night-report.json`;
   email Ed the verdict; then resume the loop." Its first scripted action writes
   the heartbeat. Token economy: the prompt instructs it to delegate reduction /
   verdict / figures to Sol and Opus immediately and to read only the report JSON
   itself.
4. **Dead-man:** a second LaunchAgent at 07:00 fires the courier only if
   `night-report-emailed.marker` is absent.

## Where I disagree with the packet or the rulings' ordering

1. **The packet's gap list solves the wrong night.** G-1/2/4/6/9 are all
   pack-path work; T1's G2-a night never touches `launch_window.py`, an arm
   receipt, or a T-0 census. Sequencing them first would spend the whole lane
   before a single unattended evening happened. Three unlisted gaps (G-10 no
   runnable script producer, G-11 no notification channel at all, G-12 no process
   predicate in the campaign guard) are the actual stage-1 content.
2. **The brief mis-cites the T26 600 s** as a relaunch liveness bound. It is a
   clock-evidence bound on the ordinary monotonic clock with an explicit
   11×45 s + 105 s derivation (`COLD-GATE-RULING.md:202-215`). Reusing it for the
   heartbeat would re-commit the defect that ruling struck.
3. **The packet prices the refusal code as "contract churn."** For a
   launch-lineage code it is three steps and touches neither the SHA-pinned
   registry nor the `REASON_CODE_COVERAGE` gate (Q2). That removes the strongest
   stated reason to defer G-9's ruling — rule it now.
4. **E-10 may not bind a diagnostic night at all**, in which case stage 1 has
   *zero* Ed-ratification dependencies. The packet lists G-8 as a hard Ed gate
   without testing whether E-10's scope reaches a night with no arm capability to
   consume.
5. **The unattended-ness is partly self-defeating today and nobody has said so:**
   the longer nobody touches the machine, the larger `HIDIdleTime` grows, and
   `quiet_mac_prep.sh:78-80` is written to FAIL on exactly that. It is safe only
   because `idleTime` happens to be 0 on this machine right now. That accident
   must become an asserted precondition in stage 1.

**Confidence:** high on the G2-a-is-not-a-pack-night reframe, the registration
path, and the launchd/Aqua determination (all bench- or file-verified); medium on
the receipt schema shape and the 300 s heartbeat deadline, which want one Sol
cross-check and one measurement respectively.

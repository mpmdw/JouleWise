# Block 5 analysis driver: resume, step retries, one-pass defect sweep (2026-11-06)

Branch `lane/2026-11-06-b5-robust`, based on `288c094f4` (speed lane head with the
L4 cache and memoized refits). Code: `joulewise/b5_analysis/resume.py` (new) and
hooks in `joulewise/b5_analysis/dry_run.py` `run()`; `--resume` in
`scripts/run_b5_analysis.py`; two timer events in `joulewise/b5_analysis/phase_timing.py`.
Tests: `tests/b5_analysis/test_resume.py`.

Ed's question was why one defect stops a whole ~150 min run with no way to resume.
After this change:

| What happens | Before | After |
|---|---|---|
| The process dies (kill, crash, power, OOM) in step N | full rerun | `--resume` reruns step N; steps 0, 1, 3, 3b rebuild their in-memory state (about 15 min on dry-j timings, mostly 3b) |
| Wall-deadline firing, lost worker observer, dead pool worker in step N | `tooling_refusal`, full rerun | step N reruns serially from its checkpoint, at most twice; the record is the uninterrupted one |
| k defective kept bundles (steps 1/2) | k full reruns to find them one at a time | the run stops as before, then reports all k in one sweep |
| Any other refusal | stop | stop (unchanged) |

The slow pipeline is now the audit behind the lean release path, so this exists to
avoid full audit reruns. It does not gate releases.

## Design and decisions

1. **The checkpoint is explicit JSON.** It does not pickle `RunState` and registers
   no `copyreg` reducer. `restricted/resume/checkpoint.json` is written atomically
   (temp file plus `os.replace`) before step 0 and after every step. It holds:
   - the binding: mode, analysis commit, checkout refusal and exception class,
     window-index sha256, store-mode token, synthetic flag;
   - the number of completed steps, the `stopped` flag, and the steps whose
     function ran;
   - the step records and their raw codes, the registered outputs in registration
     order, the runner's log counter, and the bundle run ids behind the step-1/2 logs;
   - the record's attempts/windows/census parts and the run flags;
   - the sha256 of every regular file under `restricted/`, except `resume/` and the
     live timer logs.

   Restricted tier only.
2. **Only four steps build in-memory state.** Their registered functions run an
   in-process builder: step 0 `prepare_initial`, step 1 `prepare_kept`, step 3
   `prepare_tripwires` and step 3b `prepare_brackets`. Every other step changes only
   files, records, raw codes, outputs and members. Resume re-runs exactly the builders
   whose step ran. They run through the same runner seam, against scratch custody
   (`restricted/resume/rebuild`). This is verified, not assumed:
   - each output a builder registers must have the checkpointed name and sha256;
   - the rebuilt attempts, windows and flags must equal the checkpoint;
   - the rebuilt census must be a subset of the checkpoint's census.

   Any mismatch refuses the resume. A wall-deadline firing during the rebuild
   reruns it serially, at most twice. The record's census on a resumed run is the
   union of the live census and the checkpointed census, keyed by (window, path).
   This covers any archive read by in-process code after 3b that the rebuild does
   not repeat.
3. **Rollback before a rerun.** Every checkpointed file is re-hashed first, and any
   difference refuses. Then everything a crashed or refused attempt left behind is
   moved to `restricted/resume/abandoned/<n>/` (kept as restricted evidence, never
   deleted), and new empty directories are removed. This fixes the draft's step-8
   and step-11 failures, where the partial outputs plus `RunState.write`'s `'xb'`
   open gave `unclassified_refusal`. On a resume in a new process, the old process's
   timer logs move too, so the new run opens its own. A retry in the same process
   keeps its open logs.
4. **The record write is safe at every point.** A crash after the record write but
   before cleanup: `--resume` finds a complete canonical record and only reports it
   (`resume: run already complete`, same stdout line, same exit code). A torn record
   (the crash hit inside its single `write()`) is not canonical JSON, so it is set
   aside and rewritten. After the record write the checkpoint is deleted. `resume/`
   is removed when it is empty, so a clean run leaves no trace.
5. **Retry happens at the step level, in the driver. `RunState.invoke` is untouched.**
   The cloud draft rewrote `invoke`, and `test_one_decoder_serves_r1_and_this_branch`
   pins `invoke` to r1, so that rewrite was dropped. A step is retried only for the
   refusals in the table below that have a producer here. The retry:
   - restores the checkpoint before the step: explicit fields on a shallow copy for
     a non-builder step (verified against the record parts), a full rebuild for a
     builder step;
   - sets workers to 1 on the run state and the run caches, shuts down the member
     pool, and clears the run's `worker_observer_unavailable` flag. That flag is
     sticky and belongs to the discarded attempt;
   - reruns the step, at most `MAX_RETRIES = 2` times;
   - restores the configured worker count afterwards, whatever the outcome.

   Each retry is logged to `restricted/resume/recovery.jsonl` (step, attempt,
   reason, files moved, rebuilt) and as a `step_retry {step, attempt}` event in both
   timer tiers. A data refusal is never retried.
6. **The 120 s wall deadline is unchanged on a retry.** "Frozen is not sacred"
   allowed changing it, but the evidence says no. `powermetrics_fiducial.py`
   serializes `wall_budget_s` into the reproducible `detection_projection` receipt
   of every governed invalid-evidence disposition, including the deterministic
   cell-budget one (lines 1527-1545). A relaxed budget can therefore change a
   derived byte. The retry's lever is serial execution, which removes the run's
   self-contention.
7. **No invented refusal codes.** The draft's `analysis_child_timeout`,
   `analysis_refit_budget_exhausted`, `analysis_worker_died` and
   `analysis_resume_checkpoint_invalid` have no producer, so they were not added.
   `configs/analysis/b5/dry_run_refusal_classes.json` is unchanged. A refused resume
   prints `resume refused: <reason>` and the usual `step 0 - tooling_refusal` before
   any record exists, the same pattern as a custody preflight refusal. The draft's
   `retry_budget_multiplier`, which had no consumer, is gone.
8. **The one-pass defect sweep covers steps 1 and 2 only.** It runs after the
   record and its sidecars are written, so it cannot change the record, the step
   codes or the exit code.
   - **When it runs:** the stopping row is at step 1 or 2 and is neither retryable
     nor an outcome.
   - **What it does:** runs every kept bundle through strict validation, then
     re-reduces every bundle that passed and checks the refit-dependent fields
     against the stored summary.
   - **How:** serially through the runner seam, or through the child pool when the
     run has workers and the plain `StepRunner`.
   - **Where output goes:** custody `restricted/defects/` (`DEFECTS.json` plus the
     sweep's own logs).
   - **Firings:** a unit whose refit fired the wall deadline, or could not be
     observed, is listed as `tooling_inconclusive`, not as a defect.
   - **What stderr shows:** counts per step and window only, for example
     `defects step 1 alpha 3`.
   - **Never** excludes a unit.

   Steps 4 and 10 are not swept. Each has two per-pack units, and their inputs
   are the whole step-1/2 output of the pack, so a sweep finds at most one more
   defect. Later steps are joins over every unit, so nothing independent of a
   defect remains.
9. **Resume is for interruptions, not code changes.** A checkpoint binds the
   analysis commit. A defect fix means a new commit, and therefore a new run. A
   record binds one `analysis_commit`, and outputs of earlier steps from older code
   would not be what the record claims.
10. **No `fsync`.** `os.replace` is atomic against a killed process, which is the
    case this exists for. After a power loss a torn checkpoint fails to load and the
    run starts over. Measured cost: under `taskpolicy -b`, fsync made the 25-test
    driver acceptance class take 243 s instead of about 20 s.

## Refusal classification (what the driver does with each class)

`configs/analysis/b5/dry_run_refusal_classes.json`: 196 tooling codes, 2 outcome codes.

| Class | Producer (this tree) | Driver action |
|---|---|---|
| `calibration_wall_deadline_fired` | `run()` step loop: the run's `sys.monitoring` observer counted a `detect_pulses` return with `projection_budget_trigger == 'wall_deadline'` during the step (driver process; child firings through `_account_deadlines`, member firings through `account_outcomes`) | serial retry from the step checkpoint, at most 2 |
| `calibration_deadline_observer_unavailable`, run observer present | `_account_deadlines` (a child result without an observer) and `account_outcomes` (a member worker without one) via `run_caches.worker_observer_unavailable` | serial retry (no worker pools on the retry), at most 2 |
| `calibration_deadline_observer_unavailable`, run observer absent | `run()`: `observe_wall_deadline()` yielded None (no free `sys.monitoring` tool id) | no retry: persistent for the process |
| `unclassified_refusal` with escaped `BrokenProcessPool` | `parallel.dispatch` (`future.result()` after a worker death) out of the step 1/2/4 pool paths. `pack_map` and `member_map` already recompute serially after a worker failure. | serial retry, at most 2 |
| `unclassified_refusal`, any other escaped exception | a program or driver bug, or a host fault with no known transient signature | no retry. A host death is covered by `--resume`. |
| timeout | none: no driver, child-pool or member-pool timeout exists (the 2 s L4 custody probe returns "absent" and does not refuse) | nothing built |
| the other 194 registered tooling codes (deterministic tooling and data validity) | named refusals of the programs and the driver | no retry. A step-1/2 stop triggers the defect sweep. |
| `outcome_class` (2 codes) | registered outcomes | never retried, never swept; step 9b's non-issuance stays non-stopping |

## How to use it

```sh
# interrupted run (any exit without a record, or a record but a leftover checkpoint):
python3 scripts/run_b5_analysis.py --mode blind-dry-run --index <index> --custody <same root> --resume \
    [--workers N] [--phase-log <NEW path>]
```

The same commit, a clean checkout, the same index and the same `JOULEWISE_B5_VDL`
are required, and the refusal reason says which one differs. The worker count may
change, because it never changes outputs.

**Unit tests** (`tests/b5_analysis/test_resume.py`, `test_resume_correctness.py`; all pass):

- Boundary kill at every checkpoint, positions 0-13 (before step 0 through after
  step 11, before the record). In each case the resumed run gives the same exit
  code, record bytes, stderr and restricted tree (outside `resume/` and the timer
  logs), and no checkpoint is left.
- Kill after the first and after the last runner invocation of every step (all
  13 steps): the same equalities. This covers the draft's step-8 and step-11
  failures. Partial outputs are set aside under `resume/abandoned/`.
- A kill after the record write reports the run. A torn record is set aside and
  rewritten. A resume after the checkpoint was cleaned up reports the record.
- A different commit, a changed checkpointed file (including on the
  complete-record path), a builder that refuses on rebuild, and a release whose
  dry-run admission changed each refuse the resume with a named reason.
- Retry with real producers:
  - A real `detect_pulses` refit with a forced wall-deadline firing, seen by the
    run's real observer, is retried once. The record, stderr and tree equal the
    uninterrupted run, and a `step_retry` line validates in the structure tier.
  - A deadline that keeps firing stops after 2 retries, as `tooling_refusal
    calibration_wall_deadline_fired`.
  - A spawned pool worker calling `os._exit` gives a real `BrokenProcessPool` out
    of `parallel.dispatch`. The serial retry gives the pooled run's record and
    non-log tree.
  - A plain-runner pooled step with a lost worker observer and a speculative
    later worker is retried, then also resumed after a crash. Record, tree and
    log counter are equal.
  - A data refusal is never retried.
  - A firing over a step-6 outcome is retried, and the final record is the
    outcome record (exit 3).
- Defect sweep: alpha and gamma fail strict validation and beta fails reduce.
  The sweep reports exactly (1, alpha), (1, gamma) and (2, beta). The record
  bytes equal the unswept run, stderr gains only the defect count lines, and
  there is no marker on stderr. A refusal at step 5 runs no sweep.
- Checkpoint write skipped (injected `OSError`): resume uses the last good
  boundary, and retry never uses a stale one.

## Open issues

- **Resume cost on real data.** A resume re-runs the step 0/1/3/3b builders,
  about 15 min on dry-j timings, mostly the step-3b refits. That is still far
  below a full rerun, but it is not free. Checkpointing the bracket objects
  themselves would need a serialization of the frozen bracket types. Not done.
- **No real-data run has used this yet.** The first real use will be the next
  audit run of the slow pipeline. Production retry and sweep paths have only
  synthetic evidence: forced firing, killed worker, refusing doubles.
- **The sweep covers steps 1 and 2 only.** Steps 4 and 10 are excluded for the
  reason in decision 8.
- **One review finding was rejected.** The executing review of `bd4e141a9`
  (local Sol 6.1 xhigh) found five issues. Four were adopted in `21ea4d321`:
  - complete-record integrity;
  - cleanup-then-crash reporting;
  - refused-builder rebuild;
  - release admission on resume.

  The fifth, "never retry a firing step whose masked attempt held an outcome", is
  rejected. The retry decision must read only the host signal: retry-or-not is
  visible in the structure tier, so conditioning it on the hidden result would
  reveal that result. The rerun reaches the same record an operator's full rerun
  would. The test asserts the opposite of the finding.
- **Other drafts and agents.** The earlier wrong-base drafts are superseded and
  not adopted: `wip/b5-robust-solA` (pickled `RunState`, sibling probes, an edit
  to the r1 equivalence assertion) and `wip/b5-robust-solB` (a 198-code retry
  class file). They are local worktrees under `jw-wt/`. The cloud draft
  `sol/burn-robust` (`bdc415538`) is superseded too. The speed lane
  (`lane/2026-11-06-b5-under-90`) also edits `run()`, so whichever lands second
  rebases.
- **Resume after a code change is refused by design** (decision 9). A
  `--phase-log` path must be new on resume, because the structure log refuses an
  existing path.

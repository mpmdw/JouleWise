## Safety checks

**No signals.** Grep found no `killpg`, `renice`, `pkill` or `taskpolicy` in the PR. `os.kill` appears in one place: `ledger.py:235` (`exit_like`) sends the child's terminating signal to the wrapper itself, so that it exits the same way the child did. `ledger.py:179` forwards SIGTERM and SIGHUP to the wrapper's own child only. The only other kills are by `subprocess.run(timeout=…)`, which kills the watcher's own `git`/`gh` children on timeout (`alarms.py:138`).

**No SSH.** `RL128_PROBE_ENABLED = False` and `RL128_CALIBRATION_RECORD = None` are module constants (`sources.py:59-60`). `load_config` only fills the config dict and never touches them. Even when both are enabled, the probe body raises `NotImplementedError` (`sources.py:75`). `test_rl128_probe_is_disabled` and `test_host_command_sites` pass.

**Writes.** The watcher writes only to these places:
- `/Volumes/JW-EXT/ledger/{timing.jsonl,alarms.jsonl,watch-heartbeat.json,profiles/}`
- `~/Library/Application Support/JouleWise/pipeline-watch/`
- `~/Library/Logs/JouleWise/`
- the shared git store (see F1)
- GitHub issues

It does not write to custody paths, `~/night-*` or any working tree. `/Volumes` is `drwxr-xr-x root`, so with JW-EXT unmounted no `mkdir` can create a shadow `/Volumes/JW-EXT`. Every such `mkdir` fails with OSError, which is caught. The report script writes `docs/run_reports/…` into its own checkout, but only when run by hand, and never from the LaunchAgent.

**launchd.**
- `StartInterval` is 120, with no `KeepAlive`, so it cannot crash-loop.
- It runs at `Nice` 10 with `ProcessType` Background.
- The wrapper exits 0 and posts one notification per hour when the checkout or the ledger dir is missing.
- `single_instance` uses flock, so overlapping polls are skipped.

**Growth.**
- `alarms.jsonl` is bounded by the dedupe: one line per key per hour for alarms, per 6 h for warns.
- The log is about 45 KB a day.
- A profile is written once per raised, profiled key, at about 40 KB or less each.
- Resolved state is pruned after 7 days.
- None of these files rotates, which is acceptable at these rates.

**Issue dedupe.**
- `plan()` posts at most one create or comment per key per 6 h, plus one close per resolve. The bound holds only while the state saves (see F2).
- Resolve closes only `record["issue"]`. That number comes either from the watcher's own `gh issue create` output or from an open issue that carries the `pipeline-alarm` label and the watcher's body marker for that key (`alarms.py:178-231`). It cannot close any other issue.

**Failure modes.**
- If `gh` is unauthenticated or the network is down, the calls return non-zero, the channel logs `failed`, and `last_issue_s` is already stamped. There is no retry storm.
- `WATCH_SOURCE_FAILED` fires after 3 consecutive failures, through the local channels.
- Worst case with the network down is about 5 min per poll, from the timeouts of 90+60+60+60 s. launchd does not overlap polls.

**`timing_ledger.py`.**
- The exit code is kept exactly, including 127 and 126 for not-found and not-permitted.
- A child killed by a signal is re-raised on the wrapper, after `SIG_DFL` is restored.
- stdin, stdout, stderr and every fd are inherited (`close_fds=False`). The SIGINT and SIGQUIT dispositions are set only after `Popen`, so the child keeps its defaults.
- If `send_signal` reaps the child first (its internal `poll()`), the `ChildProcessError` fallback handles it.
- Ledger write failures never raise.

The real-child tests confirm exit 7 with piped stdin, stdout and stderr, and confirm that a SIGTERM death is re-raised as -15.

## Findings

### F1 (Medium, fix before install): every poll writes `refs/remotes/origin/main` in the shared `handoff` bare repo

- **Where:** `joulewise/pipeline_time/sources.py:133-134` and `scripts/pipeline_time_report.py:46-47`.
- **Cause:** `git fetch origin +refs/heads/main:refs/pipeline-watch/main` also updates the remote-tracking ref `refs/remotes/origin/main`, because of git's opportunistic remote-tracking update.
- **Verified:**
  - `git rev-parse --git-common-dir` is `/Volumes/JW-EXT/air-home/code/CapstoneProject/jw-wt/handoff/.git`, the bare repo behind about 30 lead worktrees.
  - presign-ci, which the PR's install step uses, shares the same common dir.
  - The reflog shows `refs/remotes/origin/main@{2026-11-13 06:50:26}: fetch --quiet --no-tags origin +refs/heads/main:refs/pipeline-watch/main: fast-forward`.
- **Failure scenario:**
  - Every 120 s, the watcher takes the `refs/remotes/origin/main.lock` that every lead worktree's fetch also needs. A concurrent lead `git fetch` or `git pull` then fails with "cannot lock ref".
  - If GitHub stalls and the 90 s timeout SIGKILLs `git fetch` during the ref-update phase, a stale `origin/main.lock` is left behind. Every lead fetch then fails until someone deletes the lock by hand.
- **Fix:** add `--refmap=` (empty value), which turns off the opportunistic update. Optionally also add `--no-write-fetch-head`:
  `["git","-C",repo,"-c","maintenance.auto=false","-c","gc.auto=0","fetch","--quiet","--no-tags","--refmap=","--no-write-fetch-head","origin","+refs/heads/main:refs/pipeline-watch/main"]`.
  - After the fix, the only shared writes are the private ref and additive objects.
  - Add a one-line test that asserts `--refmap=` is in the fetch argv.

### F2 (Medium, fix before install): a failed state save turns the issue channel into a comment every 120 s

- **Where:** `scripts/pipeline_watch.py:104-122`, with `alarms.save_state` at `alarms.py:70-83`, which re-raises.
- **Cause:** the order is `deliver()` (posts issues) and then `save_state()`.
- **Failure scenario:**
  1. The internal disk fills (this has happened on these machines before), so `mkstemp` or `json.dump` raises after `deliver`.
  2. The poll dies, and the new `last_issue_s` is never saved.
  3. On the next poll, `plan()` sees the key as new and raises it again.
  4. `open_issues()` finds the existing issue by its marker, so the watcher posts "Still active" on it.
  5. Steps 2-4 repeat every 120 s for every active alarm key, which is 720 comments a day per key on a public repo.
- **Fix:** save the state right after `plan()`, before any channel. If that save fails, deliver only the local channels (skip `issues`), then save again after `deliver` to record the issue numbers. Add a test with `save_state` patched to raise, checking that the issue channel goes silent.

### F3 (Medium, fix before install): one failed `git fetch` falsely resolves RUN_STATE alarms and closes their issues

- **Where:** `sources.py:133-140`. When the fetch fails, `text` is None, so `snap.run_state` is None. ARM_MISSING, SESSION_OVERDUE, CLOSE_ITEM_MISSING, REFUSED/FAULT_ITEM and MBP_IDLE then all return nothing.
- **Failure scenario:**
  1. SESSION_OVERDUE is active, with an open issue.
  2. One fetch stalls (a 90 s timeout on GitHub's git endpoint), while the gh API still works.
  3. `plan()` resolves the key: a desktop "RESOLVED SESSION_OVERDUE" notification goes out, and `gh issue close` posts "the watcher no longer sees" on the issue.
  4. On the next poll the key returns, but `last_sent_s` is under 1 h old and `last_issue_s` is under 6 h old. It re-activates silently, and the issue stays closed for up to 6 h.

  A real strand looks resolved during exactly the hours it matters.
- **Fix:**
  - When the fetch fails, still run `git show refs/pipeline-watch/main:RUN_STATE.md`. The last good copy is stale by at most a few polls.
  - Count the failure either way.
  - Optional: in `plan()`, do not resolve keys whose source failed this poll.

### F4 (Medium, fix before install): "NOTHING ARMED" reads as an arm and can suppress MBP_IDLE indefinitely

- **Where:** `runstate.py:28`. `NEGATION_RE` lists `NOTHING IS`, `NOT`, `NEVER` and `NO`, but not `NOTHING` alone or `NOTHING WAS`.
- **Probe:**
  - `classify("…Part A FAILED; NOTHING ARMED")` returns `{armed, fault}`.
  - `classify("…so NOTHING WAS ARMED")` returns `{armed}`.
  - "NOTHING ARMED" is house phrasing: it appears ten times in RUN_STATE, at lines 4957, 4974, 4991, 5100 and others. All of these are old unnumbered handoffs today, but a future numbered heading will use it.
- **Failure scenario:**
  1. A magistrate refusal heading says "Part A FAILED; NOTHING ARMED".
  2. `session()` takes it as the latest arm. It has no plan id and no latest end, so SESSION_OVERDUE never fires.
  3. `mbp_state` returns `armed` until some later CLOSED or REFUSED heading.
  4. FAULT_ITEM clears at the next lead item, but the MBP then sits idle with MBP_IDLE suppressed. That is the exact condition RL-127 wants caught within 30 min.
- **Fix:** extend the negation to `NOTHING(?: WAS| IS)?`, `WAS NOT` and `NOT YET`. Add the two probe headings to `test_pipeline_time_detect`.

### F5 (Medium-Low, strongly recommended): a persistent exception kills the watcher silently

- **Where:** `scripts/pipeline_watch.py:79-129` has no top-level guard.
- **Failure scenario:** a bad `/Volumes/JW-EXT/ledger/watch-config.json` override crashes `local_job_candidates` with a KeyError on every poll. The same happens with a `local_jobs` row that has no `pattern`, a non-numeric `budget_s`, or a hand-edited `mbp-queue.json` with a string epoch. Each poll then writes a traceback to the log (about 1 MB a day) and alarms nothing. Nothing reads `watch-heartbeat.json`.
- **Fix:**
  - Wrap the poll in `except Exception`.
  - Post `ALARM PIPELINE_WATCH_CRASH` through `osascript` and `alarms.jsonl`, rate-limited by a stamp file (hourly, the same pattern as the wrapper's `repo-missing.stamp`).
  - Print one log line and exit 0.
  - Separately, the lead's own lane watcher should treat a heartbeat older than 10 min as "watcher down".

### F6 (Low-Medium, follow-up OK): local-job rules match shell wrappers and seat prompts by their full argv

- **Where:** `detect.py:326-349`. `rule_for` regex-searches the whole command line, and the top-most matching ancestor becomes "the job".
- **Failure scenario:** each of these raises LOCAL_JOB_OVER, a `sample` profile and a public issue on a process that is not a job:
  - A lead lane watcher such as `zsh -c '… until ! pgrep -f independent_recompute_b6; do sleep 60; done'` matches `block-analysis` and alarms at 1.5 h.
  - A `codex exec "<prompt mentioning rehearsal / b6_r12_ / unittest>"` seat matches and alarms at 3 h or 45 min.
- **Fix:**
  - Let only interpreter processes match a rule: argv0 basename `Python` or `python3*`, with the script or `-m` module as one of the first three args. Wrapper shells and `time`/`env`/`taskpolicy` then stay out of the matching.
  - Alternatively, add exempt rows for `/.claude/shell-snapshots/` and `codex exec`.

### Low findings (follow-up)

- **L1 (`runstate.py:236`): any lead heading with an upper-case CLOSED, COMPLETE or REFUSED closes the armed MBP session.** For example, "Lead: R12 nine COMPLETE" during an armed night closes it. SESSION_OVERDUE and CLOSE_ITEM_MISSING then go blind, and the results-branch `ls-remote` stops. Suggested fix: accept a lead closer only when its heading names the plan id, the arm item number, or "night" or "R1". Legitimate lead closers today, such as items 250, 253, 262 and 300, all say R1 or night.
- **L2 (`detect.py:113`): ARM_MISSING checks only items after the pointer item, never the pointer item's own classes.** A magistrate item that both says ARMED and carries a pointer with "re-arm" or "install" in `next_observable`, with no `armed:` key, raises ARM_MISSING after its deadline.
- **L3 (`alarms.py:194-201`, `detect.py:275,366`): issue bodies include up to 300 characters of local argv and the cwd, and mpmdw/JouleWise is PUBLIC.** Those strings contain `/Users/edr/...`, the `Edrs-MacBook-Air` host name, scratch paths, and any `--note` text. Suggested fix: post only the code, stage, pid, elapsed time and the script basename to the issue, and keep the full detail in `alarms.jsonl` and the profile.
- **L4 (`detect.py:42`): `session_overdue_grace_s` is 0.** SESSION_OVERDUE therefore fires at the latest end, before a headless magistrate can write its close item. Consider the 30 min notice budget.
- **L5 (`detect.py:222`): the key `mbp_idle:{int(since)}` changes whenever a new pointer item lands while the MBP is idle.** Each change closes one issue and creates another. Use a fixed key, `mbp_idle`.
- **L6 (`alarms.py:204-210`): when a human closes a watcher issue, the watcher keeps commenting "Still active" on the closed issue every 6 h and never reopens it.**
- **L7 (`ledger.py`): three wrapper edge cases.**
  - `os.getcwd()` (line 147) raises if the cwd has been deleted, so the command never runs.
  - A SIGINT sent to the wrapper pid alone, rather than to the tty group, is ignored and not forwarded (line 46). This matches `/usr/bin/time`, but should be documented.
  - `Popen` errors other than not-found and permission (for example ENOEXEC) produce a traceback and exit 1, not 126.
- **L8 (`pipeline_watch.py:18-19`): the docstring says `--dry-run` "changes nothing".** It still fetches into the shared repo (F1) and creates the state dir and lock.
- **L9 (`sources.py:269`): `sample` attaches to the target's task port and briefly suspends its threads.** It sends no signal, which is fine on the Air. Remove the R12 exempt row when the nine reports, as the config says. After that, later R12 runs that match `b6_r12_` are profiled at 3 h.
- **L10 (CI_RUN_SLOW noise):** main's state-only CI runs about 16 min against a 7.5 min trigger, and 202 of 237 pushes are state-only. Expect a warn notification on almost every main push until state-only CI gets fast. It is warn-only, with no issues, and acceptable as a bottleneck signal.
- **L11 (PR body): the install block ends with `install_pipeline_watch.sh --uninstall`.** Do not paste the block wholesale.

## Findings

**F1 (required, medium). The planning-release measure is the whole-G0 peak, which does not
separate 3(a)'s pattern from the one I reserved.**
- `planning_released_segments` accepts `heater_key_max_c ≥ band_edge_c − 0.3`. A record with a
  peak 5 °C over the edge is accepted.
- The preheat runs full duty until the key is within 0.5 °C of target, checked once a second. The
  heater key is now TVh0, a die key (τ about 17 s, 54 °C rise). It will overshoot the edge in the
  first seconds of nearly every planning G0, so the whole-span peak passes almost always. That
  includes "a key well inside the band that still does not release", which RL-122 3(a) sends to me.
- **Fix:** take the peak over the last 300 s of the G0 interval, same threshold. A steady hold
  0.06 to 0.21 °C under the edge passes; a key crossing the edge passes; a key that sat well inside
  the band for the final five minutes is refused. Rename the field so the window is in its name
  (for example `heater_key_max_last_300s_c`), state the window in the docstring and the refusal
  text, and add a test.

**F2 (required, low). The validator trusts the table's declared classification digest.**
- With the `classification_sha256` field left in place, I raised TVh0's noise in the ranking and
  the validator accepted Tf48. Editing `coverage` so TVh0 fails a smoke phase did the same. Both
  need a matching lead-written ruling file, so this is not an attack path, but RL-122 item 7 says
  "accepts exactly one slow pick".
- **Fix:** on the RL-122 path, require `smoke_sha256` to equal the regenerated table's hash
  (`b2369b6c78d91b75299e10ff7249f1e8cae7304b48cf022e20b2c6a6f69f2884`) as a kit constant, with a
  test for each of the two cases.

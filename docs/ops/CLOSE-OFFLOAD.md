# Automatic close offload

**PROVISIONAL: synthetic validation only. Do not deploy or issue the standing
item until the policy questions below are settled and the PR is admitted.**
This is an [AGENT] build; it makes no MBP contact. Live installation, GUI/TCC
access, provider behavior and host quiet remain the lead's gates.

The owner requested this on 2026-11-16 to keep measurement outputs from
accumulating on either internal disk. `scripts/close_offload.py` is the one
entry point; `joulewise/close_offload.py` owns the implementation. It hashes
and transports bytes, including receipts. It never decodes or parses a runner
receipt, journal, meter stream, model output or other measurement file. It
parses only metadata generated by this tool. Output contains operational
statuses and hashes; exception text and measurement content are suppressed.

`docs/research-audits/2026-11-10-fable/RESEARCH-LEAD-DECISIONS.md`;

## Policy questions requiring a lead/owner ruling

The requested implementation emits readable `.tar.zst` archives, following
the owner's two reference scripts, and returns nonholding `UPLOAD_PENDING`
for an unconfirmed upload of an older retained span. RL-173 A instead names
encryption with a key held off the MBP (A.1–2), requires upload completion
before the next soak (A.3), and holds unverified offloads (A.7). Neither
compression nor an archive hash establishes application encryption. A pending
iCloud sync-folder upload can continue in the provider daemon after this
command exits. **These are open policy conflicts, not established compliance.**
The implementation records `application_encryption: false`; it does not create
an encryption key or claim a key escrow exists. The two concrete choices are
application encryption plus an off-MBP key record versus an explicit owner
exception for `.tar.zst`; and holding versus nonholding pending older uploads.

Even after a ruling, iCloud Drive is RL-173 A.3's **interim sync-folder route**,
not the permanent synchronous provider API. Add `bird`, `cloudd` and
`fileproviderd` to the close maintenance line while it is used. Successful
runs synchronously wait for all their files to upload and evict. A deadline
kills the worker process group; it cannot stop the operating system's iCloud
provider daemon. No permanent-provider or hardware-validation claim is made.

## Magistrate invocation, after Check

Run from the user's GUI login domain (the magistrate's session or a
LaunchAgent), using `/opt/homebrew/bin/python3` (3.14). SSH cannot access
this iCloud container through TCC; this tool never invokes SSH or contacts
another host. The lead installs the reviewed checkout separately. Assuming
it is `/Users/edr/code/jw-close-offload`, the proposed command is:

```sh
/opt/homebrew/bin/python3 -B /Users/edr/code/jw-close-offload/scripts/close_offload.py --deadline "$CLOSE_DEADLINE_EPOCH"
```

`CLOSE_DEADLINE_EPOCH` is the hard epoch deadline selected by the controller
inside the current close interval, before the next arm/soak. It is not a
relative timeout. The command refuses a desk fence or runner, acquires the
same `.desk-fence.lock` as the launcher, rechecks absence, and holds the lock
for the whole operation. It checks runner/fence absence at every transition
and before deleting. The controller must await the command's exit and apply
its result before considering any next arm. It does not launch a span or
change the process-based quiet, minimum GAP, restore, Check or other arm gates.

A supervising process imposes the hard deadline even during filesystem or
compression I/O and kills/reaps its worker process group. Normal upload polls
stop slightly early to leave time for an orderly `UPLOAD_PENDING` exit. A
forced timeout is conservatively `DEADLINE` and holds the next arm.

## Selection and retention

The fixed default discovery roots are:

- campaign: `/Users/edr/campaign-out/<kit>/<plan>-<YYYYmmddTHHMMSSZ>/runner_receipt.json`;
- Part C/F0: `/Users/edr/code/jw-wt/*/.desk/r1-partc-*/runner_receipt.json`.

A regular receipt's presence is the structural closed signal. Its contents
are never read. Check and all restores must already have been reported by
the magistrate; receipt presence alone grants no arm authority. Missing
roots, unreadable census entries and ambiguous cloud names fail closed.
Symlink roots and symlink candidate directories are not followed.

Keep the newest receipt by nanosecond mtime **in each kind**: campaign across
its root and Part C/F0 together across its root. Keep all ties. Its entire
output stays in place and its receipt mtime is untouched, preserving the
host GAP census. The newest output's existing Check/copy obligation remains;
this rotation step cannot satisfy that newest campaign's `.ok` gate.
Normal runs rotate the next newest closed output per kind and resume any
selected older work already recorded. `--catch-up` handles all older closed
leftovers under the same safety gates and deadline:

```sh
/opt/homebrew/bin/python3 -B /Users/edr/code/jw-close-offload/scripts/close_offload.py --catch-up --deadline "$CLOSE_DEADLINE_EPOCH"
```

A nonempty `/Users/Shared/JouleWise/desk-copy/<plan>.air.ok` or `<plan>.ok`
counts as the requested prior-copy marker (the marker's contents are not
parsed). Part C/F0 uses its output basename in place of `<plan>`. Every path
still gets its own verified cloud copy. `--cloud-only-allowed` is the default:
absence of an Air marker is recorded as `copy_basis: cloud-only` and does not
prevent cloud transfer. `--no-cloud-only-allowed` requires a marker for new
work; skipped work returns a holding failure. Existing transactions resume
with the copy policy originally recorded. Existing `.ok` markers are preserved.

This retains at most the newest output of each kind plus genuine pending or
failed originals and any backlog until catch-up. It does not touch historical
`night-*` roots, sealed bundles, models, caches, registrations or raw evidence
outside these two structural output patterns.

## Transaction and records

For each selected output:

1. Build a canonical manifest: SHA-256 and size for every regular file,
   directory entries (including empty directories), and relative symlink
   targets. Refuse special files and escaping/absolute links.
2. Write a Python 3.14 stdlib `tar.zst`, then stream it back to compare the
   complete member set, file sizes/hashes and link targets. Rehash the source
   tree to detect changes. Hardlinked files are stored as independent bytes.
3. Write a receipt containing the manifest, its SHA-256, and the archive's
   SHA-256 and size. Stage both privately under
   `/Users/Shared/JouleWise/close-offload/stage/<source-path-sha256>/`.
4. Install archive and receipt under the private iCloud Drive folder
   `~/Library/Mobile Documents/com~apple~CloudDocs/JouleWise-offload/spans/<kind>/<name>.tar.zst`
   and `<name>.receipt.json`. Hash the installed bytes and stream-verify the
   installed archive. Never overwrite a foreign or mismatching cloud object.
5. Poll `brctl evict` for both objects. Only
   `NSFileProviderErrorDomain -2008` is a retryable not-uploaded response;
   other errors hold. A successful eviction must also show native `dataless`
   flags through `stat -f %Sf` and the expected logical byte size. Sparse
   allocation is never used as upload evidence, especially for small receipts.
6. Record each object's provider confirmation immediately. Preserve the
   original until **both** cloud objects have confirmed upload and eviction.
   Rehash the original once more, persist `DELETING`, delete it, then persist
   `COMPLETE`. Interrupted deletion resumes only if the remaining entries
   match a subset of the verified manifest. New files are never swept up.

The controller-readable record is:

```text
/Users/Shared/JouleWise/close-offload/records/<sha256-of-absolute-source-path>.json
```

Schema `joulewise.close-offload.v1` records `source`, `kind`, `archive`,
`manifest_sha256`, `archive_sha256`, `archive_bytes`, `receipt_sha256`,
`cloud_only_allowed`, `air_marker_observed`, `copy_basis`, `state`, and
per-object `provider` confirmations (logical size, command/readback and time).
States are `PACKED`, `UPLOAD_PENDING`, `EVICTED`, `DELETING`, `COMPLETE`.
Stage receipts remain small local metadata; local staging archives are removed
once installed and verified in iCloud. A new campaign `.ok`, if needed, is
written only after successful completion and contains this record. No failure
writes a copy marker. These private artifacts must never be committed,
uploaded to releases, attached to PRs or stored in this PUBLIC repository.

Exit codes and final JSON are the controller interface:

| Exit | Status | Original / cloud archive | Next arm |
|---|---|---|---|
| 0 | COMPLETE or AIR_VERIFIED | original evicted only after verification; newest kept | existing gates apply |
| 20 | UPLOAD_PENDING | original retained, cloud archive retained; resume later | requested nonholding policy **awaits ruling** |
| 21 | verification, I/O, metadata or copy-policy failure | preserve original unless already verified deletion began | hold, F0 included |
| 22 | DEADLINE | preserve unfinished evidence; verified deletion can resume | hold, F0 included |
| 23 | fence, runner, census error or launch lock busy | no transfer started, or stop at next safety checkpoint | hold, F0 included |

The final JSON includes `status`, `holds_next_arm` and completed count. Do not
collapse all nonzero statuses into a successful copy; neither pending nor a
skipped original creates an `.ok` marker. No content from a path is printed.

## Air pull to the external SSD

The lead supplies the independent `receipt_sha256` from the MBP's private
record to the Air (metadata only). A receipt cannot authenticate itself. Run
from the Air's GUI domain, with the same iCloud account:

```sh
/opt/homebrew/bin/python3 -B /Volumes/JW-EXT/jw-wt/close-offload/scripts/close_offload.py --air-pull "campaign/$SPAN_OUTPUT_BASENAME" --receipt-sha256 "$OFFLOAD_RECEIPT_SHA256" --deadline "$PULL_DEADLINE_EPOCH"
```

`partc/<basename>` selects Part C/F0. This requests hydration, checks receipt
identity and its independently supplied hash, checks archive size/hash,
stream-verifies every member, extracts with the standard library data filter,
and rehashes the extracted tree. It atomically publishes only a complete
verified tree under `/Volumes/JW-EXT/cadence-desk/<kind>/<name>/`.
Existing identical destinations are idempotent; different destinations refuse.
Partial extraction is on the external SSD, never the Air's internal disk.
It re-evicts the Air's iCloud cache on success and reports any eviction failure.
The restored campaign's original `desk-bundle` is inside that tree; the desk
controller chooses its existing input layout. No analysis is run here.

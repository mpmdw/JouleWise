Project README · undergraduate capstone · local LLM energy

JouleWise is an extensible measurement harness.

Measure first.
Make claims second.

JouleWise runs language-model inference on local hardware, records power and runtime events together, and seals the evidence into a bundle that can be checked after the machine has gone quiet. The goal is not a prettier leaderboard. It is a defensible way to ask where the joules went.

What it is

Instrument first, benchmark second.

Harness · the instrument

Runs, observes, and preserves.

Typed experiment configs, runtime adapters, telemetry adapters, bundle writing, reduction, and strict validation form the reusable measurement harness. New hardware and runtimes plug into these seams.

Benchmark · a governed use of it

Freezes workloads and rules.

A benchmark is the frozen workload suite, run rules, and strict validator layered on the harness. Calling the whole repository a benchmark would hide the distinction that makes its evidence reusable.

This terminology is binding reader-facing policy under D-069. The harness can exist before a benchmark campaign is ready to support a comparison.

Why it exists

Energy numbers are easy to print and hard to mean.

boundary

What did you measure?

Chip rails, package power, and wall power answer different questions. JouleWise names the boundary beside the result.

time

When did measurement begin?

Model loading, sampler startup, prefill, decode, and cooldown must not drift into one another unnoticed.

noise

Could the instrument resolve it?

A small difference may be below the detection floor. “Not resolvable” is not the same claim as “no difference.”

evidence

Can someone check it?

A summary without its trace, events, configuration, and provenance is an assertion. A strict-valid bundle is an audit trail.

How it works

One path from intent to evidence.

  1. config

    Describe the run.

    Model, workload shape, runtime, telemetry backend, repetitions, and evidence rules begin as typed inputs rather than shell-history folklore.

  2. adapters

    Exercise the target.

    The controller pairs a runtime adapter with a telemetry adapter while recording lifecycle, phase, and token events.

  3. bundle

    Keep the raw record.

    The normalized config, metadata, event log, raw telemetry, outputs, logs, and reduced metrics live together as immutable evidence.

  4. strict

    Re-derive, do not merely inspect.

    Strict validation parses the raw evidence again, recomputes metrics, checks provenance and completion, and fails closed on contradictions.

  5. claim

    Ask what the evidence allows.

    Detection floors, uncertainty, analysis plans, and the claims ladder decide whether a number is descriptive, comparative, or not yet claim-bearing.

Current state

A research prototype with a real evidence path—and unfinished claim gates.

Working now

The Mac path runs MLX inference with powermetrics telemetry, creates strict-valid bundles, and re-derives results from preserved evidence. The analysis and claim-gating machinery is implemented.

Newest evidence

The Window-A floor collection is complete and independently verified. It produced usable floor estimates, but every contributing bundle carries claim-evidence flags. The numbers are calibration evidence, not permission to overstate a model comparison.

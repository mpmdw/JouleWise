## Gate machine and custody

Issue, Start and Run load the frozen `tests/hp02_gate_machine/GATE-MACHINE.json` from the reviewed checkout. Keep that file with the item generator. The machine distinguishes clock-only waits from outcomes that record an open hold. The guard also protects every backwards-feasible counted start after subtracting the entire fence, external transfer and demonstrated startup bound.

The append-only ledger stores the fact, source digest, attempt time, sequence and hold ID. Issue records retain the same issue ID through proposal and publication. Holds for an unreadable issue identity, ledger failure or unfinished read are keyed by admitted queue SHA and position in the separate `/Users/Shared/JouleWise/hp02-holds` custody root. Restoring the primary store or obtaining a different issue at that position leaves its holds open. A canonical failed-read record contains `source`, `error_class`, `attempt_time` and `ledger_sequence`. SHA-256 covers the compact sorted-key JSON of that record. A changed immutable receipt projection under the same digest records a separate hold.

Use `hold_dispositions` in a current observation to request clearance. Each disposition uses schema `hp-02.hold-disposition.v1`, action `clear`, the exact `hold_id`, `source_digest`, and either `issue_id` or `queue_sha` with `queue_seq`. Its `ledger_sequence` must exceed the hold's sequence. The `authority` names the `role` (`lead` or `magistrate`), integer `run_state_item` and full Git `commit`. Publish the exact payload in a fenced `hp-02-hold-disposition` block under the cited ISSUED RUN_STATE item. The published block omits `authority.commit` because its commit contains that block. Use a current `origin/main` on the measurement checkout. The gate verifies the published owner, payload, binding and sequence, then reassesses current evidence.

Observed `lm-hp-01` execution is a shared terminal fact. Only a separate lead `ATTESTATION-CORRECTION` can retract it. Publish an `hp-02-attestation-correction` block and supply its record in the observation's `attestation_corrections`. It uses schema `hp-02.attestation-correction.v1`, action `ATTESTATION-CORRECTION`, `look_id` equal to `lm-hp-01`, `original_source_digest`, `evidence` containing a provenance record ID and SHA-256, a later ledger sequence and the lead's authority. The cited evidence identifies the mistake in the original attestation. Current execution, other holds and the spent and host-halt bars still apply.

A final read that finds a new block refuses and records the fact before releasing the unused claim. A successful final read stays write-free through invocation.

## Typed records

Every record below with provenance carries `record` identifying the source evidence and `by` naming its responsible seat. Use JSON with epoch seconds for clock fields and lowercase SHA-256 hex for digests. The issuing desk and magistrate must reconcile conflicting or missing observations at their source before attesting.

The issue object has schema `hp-02.issue.v1`, provenance, `status` (`PROPOSED` at Issue and `ISSUED` thereafter), `issued_epoch_s`, an optional finite `expires_epoch_s` (null for no age expiry), `check_deadline_epoch_s`, `check_target` and `latest_close_at_issue` (the latest Check's record ID). Copy the selected item's `authority` fields to the issue top level. Its `binding` consists of the selected item's `span`, `piece`, `attempt`, `legs`, `pin`, `kit_sha`, `queue` and `predecessor`. The Check deadline is a reporting target. The queue interval controls admissible t0.

The observation has schema `hp-02.observation.v1`, provenance, `phase` (`Issue`, `Start` or `Run`), `host`, the same `binding`, `issue_record` (the issue record ID), `observed_epoch_s`, `valid_through_epoch_s` and `fence_clear`. Supply these evidence objects with their own provenance. In Run, `observed_epoch_s` is the earliest current sample in the envelope. Each evidence object below supplies its own `sampled_at` epoch for when it was checked for Run. Historical receipts retain their original event times.
